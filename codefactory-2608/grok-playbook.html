팩트 설계 원칙 대응표 아이디어 10 프롬프트

결론 먼저

그록봇의 본질은 모델이 아니라 세 가지 구조다 — ① 실무 최소 단위로 쪼갠 봇, ② 그 봇들을 묶어 자율 협업시키는 그룹 스레드, ③ 내 PC와 무관하게 도는 클라우드 VM.

①②는 Claude Max에서 이미 재현 가능하다. 진짜 갭은 ③과 Teach Task 두 가지뿐이다.

그리고 이 PC는 트레이딩 봇 때문에 어차피 24시간 켜져 있다. 그록봇 최대 셀링포인트인 "내 컴퓨터가 꺼져도 돈다"가 당신에겐 절반만 유효하다. 월 $200를 새로 결제할 이유는 약하고, 구조를 베낄 이유는 강하다.

쉽게 말하면 — 작은 회사 차리기

알바 한 명한테 "우리 광고 전부 봐줘" 하면, 돌아오는 보고서에 A광고 B광고 C광고가 뒤죽박죽 섞여 있다. 그래서 담당을 딱 정해서 사람을 나눈다. 그리고 같이 얘기해야 할 때만 회의실에 모은다.

1-2. 비용 — 모델은 싼데 입장료가 비싸다

실사용 체감 (영상 실측)

SuperGrok $30 플랜에서 프로젝트 5개를 동시 실행하고도 사용량 7%. 진행자 표현으로 "체감상 $100짜리 분량". 500K 컨텍스트.

강점

  • 루빅스 큐브(3D 질감 + 회전 엔진 + solve 역추적)를 5분, 싱글 프롬프트, 네이티브 HTML/JS/CSS만으로
  • 에어비앤비 클론 10분, 이미지까지 자체 생성
  • 속도 빠름(자체 서버), 검증을 열심히 하는 편

약점

  • 물리 엔진 취약 — 앵그리버드 클론에 40분 쓰고도 발사체 물리가 부자연스러움
  • 시각적 결함 미검출 — 텍스트 겹침을 "문제로 인식하지 않음"
  • 한국어 어색 — 영어는 문제없음
여기서 바로 나오는 결론 그록은 대량·저비용 구간에 최적이고, 한국어 최종 산출물과 수치·물리 정합이 걸린 코드는 Claude가 마감해야 한다. → 아이디어 07

영상 3편 중 마지막 편이 가장 값지다. "내가 이렇게 하다 망했다"가 그대로 나오기 때문이다. 이건 그록봇 얘기가 아니라 멀티 에이전트 설계 일반론이라 그대로 이식된다.

원칙 3 — Teach Task로 절차를 가르쳐라

API가 없는 대상(에어비앤비, 메타 광고 관리자)은 결국 브라우저 조작이다. VM에서 녹화를 켜고 직접 클릭한다 → 봇이 영상을 분석해 절차를 이해하고 스킬로 저장한다. 실제 사례: 에어비앤비 접속 → 지역 검색 → 인원/날짜 → Guest Favorite 필터 → 매물 클릭 → 캘린더로 점유 확인. 이후 "지역을 주면 상위 3개 매물의 8월 숙박률을 계산해줘"가 성립한다.

원칙 4 — 단점 3가지 (그대로 옮기면 안 되는 것)

  1. 한국어 품질 — 한국어 산출물이면 Claude/Codex로 한 번 더 돌리라고 진행자가 직접 권고
  2. 진행 상태 불투명 — 작업 중인지 끝났는지 모를 때가 있다 (→ 아이디어 08에서 선제 차단)
  3. 불안정 — 리서치 프리뷰 단계. VM 접근 불가, 루틴 생성 실패, 플러그인 장애가 몇 시간 발생
"클로드 코드로도 되는데 왜?"에 대한 진행자 반박 에이전틱 AI를 써본 사람은 전 세계 5% 미만, 채팅만 써본 사람은 20%+. 나머지 90%는 배우는 것 자체가 비용인 사람들이다. 수요가 있다 = 사업성이 있다. 코딩 에이전트는 소프트웨어를 만들 때 최적이고, 그록봇류는 일상 자동화 결과물에 최적이다 — 용도가 다르다.

PART 4도출 아이디어 10

IDEA 01에이전트를 "카테고리"가 아니라 "실무 최소 단위"로 재편A · 즉시▾

당신의 하네스는 스킬 54개+를 기능 카테고리로 묶어놨다(기획/실행/검증/회고). 진행자가 정확히 그렇게 시작했다가 실패했다. 카테고리 묶음은 읽기에는 좋지만 실행 격리에는 나쁘다.

바꿀 것
프로젝트별로 실제 업무 단위 에이전트를 만들고 스코프를 문장으로 못박는다. 예: youtube-collab(협업 제안 메일만), youtube-contract(계약서만), go-signal-audit(신호 로직만, 실행 코드 금지).
스코프 계약 문장
너는 X만 담당한다. Y는 절대 읽지도 수정하지도 않는다. Y가 필요하면 @Y담당 에이전트에게 넘긴다.
주의
당신의 누적 교훈 [HARNESS][ABSORPTION] 이 여기 적용된다 — 봇 수를 늘리는 게 목적이 아니다. 기존 자산에 스코프 문장을 추가하는 게 먼저고, 신규 생성은 갭이 확인된 것만.
IDEA 02"선을 넘지 않는다" 계약을 프롬프트에 표준 삽입A · 즉시▾

그룹 스레드 데모에서 가장 인상적인 장면은 협업이 아니라 인보이스봇이 스스로 멈춘 것이다 — "PDF는 만들지만 네가 승인하기 전엔 메일을 보내지 않을게."

표준 문구
산출물은 만들되, 외부로 나가는 행위(메일 발송·결제·게시·푸시·주문)는 절대 스스로 실행하지 않는다. 준비 완료 상태로 만들고 승인을 요청한다.
왜 중요한가
이 머신에는 자금 직결 코드가 돈다. 하네스에 HITL 규칙이 이미 있지만 에이전트 프롬프트 레벨의 자기 선언은 별개의 방어층이다. 규칙 파일은 로드 안 되면 그만이고, 프롬프트 문장은 그 에이전트가 사는 한 항상 붙어 있다.
IDEA 03Teach Task 대체 — "1회 수행 → SKILL.md 자동 생성" 루프A · 갭 메우기▾

그록봇은 녹화로 절차를 배운다. Claude에는 그게 없다. 하지만 절차를 텍스트로 고정하면 동등한 결과가 나오고, 오히려 diff·리뷰·버전관리가 된다.

루프
① Claude in Chrome으로 목표 작업을 한 번 수동 유도 수행 → ② 그 세션에게 절차를 스킬 문서로 뽑게 함 → ③ 다음부터는 변수만 바꿔 스킬 호출.
방금 우리가 브라우저에서 수행한 작업을 재사용 가능한 스킬로 문서화해줘.

형식: ~/.claude/skills/<이름>/SKILL.md
포함할 것:
- 입력 변수 (내가 매번 바꿔서 넣을 값들)
- 단계별 조작 순서 (셀렉터/버튼 텍스트/대기 조건 명시)
- 각 단계의 실패 신호와 복구 방법
- 출력 스키마 (어떤 필드를 어디에 저장하는지)
- 절대 하지 말 것 (결제·삭제·설정 변경 등)

추측으로 채우지 말고, 실제로 우리가 거친 단계만 적어줘.
확인 못 한 부분은 "미확인"으로 표기해.
핵심
"추측 금지 / 미확인 표기"가 없으면 실행 안 해본 단계를 그럴듯하게 지어낸다.
IDEA 04상시 루틴 — 이미 있는 22:45 패턴을 업무 자동화로 확장A · 즉시▾

그록봇 루틴의 대응물이 이미 당신 하네스에 있다. Daily Fit 분석이 매일 22:45에 Task Scheduler로 도는 그 패턴이다. 지금은 하네스 자기점검에만 쓰이고 실제 업무에는 안 쓰이고 있다.

# Task Scheduler에 등록할 배치 (예: 매일 08:00)
claude -p "@youtube-collab 어제 도착한 협업 제안 메일을 분류하고,
신규 건은 요약 카드로 정리해서 _report/YYMMDD_collab.md 에 저장해줘.
메일 회신은 하지 마. 정리만 하고 승인 대기 상태로 둬."
필수 제약
머신 규칙 — 병렬 서브에이전트 동시 8 이하, 봉마감 창(KST 01/05/09/13/17/21시 −5~+15분)엔 3 이하. 08:00 슬롯은 09시 창을 피하니 안전하다.
IDEA 05포커스 강탈 없는 브라우저 자동화 — 전용 프로필 격리A · 갭 메우기▾

그록봇을 쓰고 싶어지는 가장 현실적인 이유가 "컴퓨터 유즈 쓰면 포커스가 나간다"였다. VM으로 해결한 문제인데, 당신은 격리로 해결할 수 있다.

방법
① 자동화 전용 Chrome 프로필 생성(작업 계정 로그인 보존) → ② connect-chrome 스킬로 전용 창 연결 → ③ 가능한 작업은 browse 스킬 headless로(포커스 개념 자체가 없음).
선택 기준
로그인 세션·CAPTCHA·MFA가 걸리면 headed 전용 프로필, 그 외 전부 headless.
IDEA 06API 없는 소스는 브라우저 대신 스크래핑 API 레이어로A · 두 영상 결합▾

진행자가 그록봇에서 브라우저 자동화로 푼 문제(에어비앤비 단가·OCC)를, 같은 진행자가 Graph Engineering 영상에서는 스크래핑 API로 푼다. 두 영상을 겹쳐 보면 답이 나온다.

조건선택
로그인 필요 · 계정 내부 데이터(메타 광고 관리자)브라우저 자동화 (전용 프로필)

IDEA 08그록봇 단점 2번을 선제 차단 — 하트비트 상태 파일B · 품질▾

진행자가 꼽은 두 번째 단점: 작업 중인지 끝났는지 모른다. 장기 자율 실행 전반의 문제다. 당신 하네스는 statusline과 obs JSONL을 이미 갖고 있으므로 고칠 수 있는데 안 고친 상태다.

규칙
5분 이상 걸리는 자율 작업은 _cache/ 에 하트비트 한 줄씩 append: {ts, task, phase, progress, next}. 종료 시 phase:"done" 또는 "failed" 를 반드시 남긴다.
효과
"돌고 있나?"를 물어볼 필요가 없어지고, 배치가 죽었는지 판별이 파일 하나 조회로 끝난다. 백그라운드 잡 중복 기동 사고를 막는 것과 같은 문제다.
IDEA 09모바일 소비 경로를 루틴 출력에 직결B · 절반 보유▾

그록봇 모바일 라이브 싱크에 해당하는 당신의 자산은 GitHub Pages 배포 습관이다. 지금은 수동 요청 시에만 배포된다.

연결
IDEA 04의 루틴 배치 마지막 단계에 publish-pages 배포를 붙인다. 아침 브리핑이 폰에서 링크 하나로 열린다.
주의 (기록된 실수)
deploy.sh 소스 인자는 절대경로 필수. 상대경로면 URL 배너는 정상 출력되면서 조용히 실패한다. 배포 후 curl로 실제 변경 문자열 서빙 확인까지가 완료다. 링크는 굵게 처리 금지.
IDEA 10"90% 시장" 논지를 산출물 전략으로 전환C · 전략▾

진행자의 반박 논지는 사실 사업 제안이다 — 에이전틱 AI를 쓰는 사람은 5% 미만이고, 나머지는 배우기 싫어서 돈을 낸다.

적용
당신이 자기 하네스를 위해 만드는 자동화 중 도메인 지식이 아니라 조작 지식이 병목인 것들은 그대로 타인용 단일 목적 도구가 된다. 범용 플랫폼이 아니라 한 직군 · 한 작업으로 좁힐 때만 성립한다.
판별 질문
"이 자동화를 남에게 설명할 때, 터미널·폴더·API 키 얘기를 빼고도 가치가 전달되는가?" → 예 이면 상품 후보.

PART 6바로 쓰는 프롬프트

1) 기존 에이전트에 스코프 계약 주입

~/.claude/agents/ 아래 에이전트 정의를 전부 읽고,
외부에 영향을 주는 행위(메일 발송·파일 삭제·push·결제·게시)를
할 수 있는 에이전트를 목록으로 뽑아줘.

각각에 대해 아래 두 문장을 삽입하는 diff를 제안해줘. 적용은 하지 마.
- "너는 <담당>만 담당한다. 그 밖의 영역은 읽지도 수정하지도 않는다."
- "외부로 나가는 행위는 스스로 실행하지 않는다. 준비 상태로 만들고 승인을 요청한다."

이미 동등한 문장이 있는 에이전트는 '이미 있음'으로 표기하고 건너뛰어.

2) 그룹 스레드형 오케스트레이션 (유튜브 팀 재현)

아래 3개 에이전트를 병렬로 띄우고, 서로 결과를 주고받게 해줘.
동시 실행 상한은 3으로 제한한다.

- collab-triage  : 받은편지함에서 신규 협업 제안만 추출. 회신 금지.
- contract-review: 첨부 계약서에서 독소 조항과 수정 필요 항목만 추출. 서명 금지.
- content-plan   : 위 둘의 결과를 받아 콘텐츠 기획안 초안 작성.

각 에이전트는 자기 담당 밖의 판단을 하지 않는다.
최종 산출물은 _report/ 에 저장하고, 나에게 승인 요청으로 끝내라.
어떤 경우에도 메일을 보내지 마라.

3) 하트비트 규칙 적용

이 작업은 5분 이상 걸린다. 진행하면서
_cache/heartbeat/<task>.jsonl 에 한 줄씩 append 해줘.

{"ts":"...","task":"...","phase":"...","progress":"3/8","next":"..."}

- 단계가 바뀔 때마다 1줄
- 종료 시 반드시 phase를 "done" 또는 "failed" 로 남길 것
- 실패해도 남길 것 (조용히 끝내지 마)
