Grok Bot 사용법과
Claude Max 이식 설계

그록봇이 실제로 무엇을 하는지 먼저 정리하고, 그중 Claude Max 구독으로 지금 당장 재현 가능한 것과 진짜 갭을 갈라낸 뒤, 이식 아이디어 10개를 우선순위로 제시한다.

결론 먼저

그록봇의 본질은 모델이 아니라 세 가지 구조다 — ① 실무 최소 단위로 쪼갠 봇, ② 그 봇들을 묶어 자율 협업시키는 그룹 스레드, ③ 내 PC와 무관하게 도는 클라우드 VM(컴퓨터 유즈).

①②는 Claude Max에서 이미 재현 가능하다(서브에이전트 + 오케스트레이션). 진짜 갭은 ③과 Teach Task(화면 녹화 → 절차 학습) 두 가지뿐이다.

그리고 이 PC는 트레이딩 봇 때문에 어차피 24시간 켜져 있다. 그록봇 최대 셀링포인트인 "내 컴퓨터 꺼져도 돈다"는 당신에게 가치가 절반이다. 월 $200를 새로 결제할 이유는 약하고, 구조를 베낄 이유는 강하다.

PART 1그록봇 팩트 시트

1-1. 그록봇이란

텔레그램·슬랙 같은 채팅 UI 위에서 동작하는 자동화 에이전트 플랫폼. 영상 표현으로는 "오픈클로 / LMS + Buzz" 포지션인데, 결정적 차이는 X가 인프라(VM)를 함께 준다는 점이다.

구성요소설명
봇 (Bot)시스템의 최소 단위. Create New Bot → 이름 지정 → 바로 채팅. 이름 자체가 메타데이터로 학습돼 역할 인식에 쓰인다("Airbnb 리서처"로 개명하면 그 정체성으로 반응).
그룹 스레드여러 봇을 하나의 스레드에 묶어 협업시킴. 영상 3편 통틀어 "가장 강력한 기능"으로 지목됨.
컴퓨터 (VM)내 PC가 아니라 X 인프라에 올라가는 가상 머신. Open Computer → 크롬 실행 → 계정 로그인 → 그 안에서 자동화. 내 PC를 켜둘 필요 없고 포커스를 뺏기지 않는다.
Teach TaskVM 화면에서 내 조작을 녹화하면 봇이 영상을 분석해 절차를 파악하고 스킬로 저장. 이후 변수만 바꿔 반복 실행.
인피니티 메모리봇별 독립 기억 + 센트럴 시스템이 전체 봇의 담당 영역을 기억. CLI 도구와 가장 다른 지점.
플러그인Gmail · Google Drive · Notion · Slack 등 연동.
루틴사이드바에서 일간/주간/월간 스케줄 저장. 특정 이벤트 반응도 가능.
모바일 앱채팅창이 그대로 앱에. 라이브 싱크되므로 데스크톱 VM에서 돌아가는 작업을 폰으로 모니터링 가능.

1-2. 접근 경로와 비용 (영상 시점: 2026-08 중순)

  • Cursor Premium Team / Cursor Ultra 결제, 또는 SuperGrok Heavy 계정 연결
  • 영상 주장: X가 Cursor를 인수했기 때문에 결제 경로가 Cursor 쪽
  • 최소 진입 월 $200 (Cursor 기준). 영상 진행자는 SuperGrok Heavy(월 $300급, 주간 리밋)를 연결해 사용
  • 진행자 평가: 초기 세팅 때는 채팅이 많지만 루틴화된 뒤엔 사용량이 충분히 여유롭다
유일한 진짜 단점 영상 3편 모두 같은 결론 — 최소 비용이 너무 비싸다. "$30 정도 쓰는 사람도 입문할 수 있게 해주면 좋겠다"가 진행자의 마무리 아쉬움이다.

강점

  • UI 카피 정확도 높음 — 에어비앤비 클론이 10분, 이미지까지 자체 생성
  • 루빅스 큐브(3D 질감 + 회전 엔진 + solve 역추적)를 5분, 싱글 프롬프트, 네이티브 HTML/JS/CSS만으로 구현
  • 속도 빠름(자체 서버 운영), 검증을 열심히 하는 편

약점 (그대로 인용 가능한 수준)

  • 물리 엔진 구현 취약 — 앵그리버드 클론에 40분 쓰고도 발사체 물리가 부자연스러움(잠깐 멈췄다 날아감). 붕괴 물리는 잘 됨
  • 시각적 결함 미검출 — 텍스트 겹침 같은 문제를 "문제로 인식하지 않음"
  • 한국어 어색 — 예전 Claude가 보이던 수준. 영어는 문제없음
여기서 바로 나오는 결론 그록은 대량·저비용 구간(반복 리서치, 스크린 요약, 초안 대량 생산)에 최적이고, 한국어 최종 산출물과 물리·수치 정합이 걸린 코드는 Claude가 마감해야 한다. 이건 아이디어 7번으로 이어진다.

PART 2그록봇 설계 원칙 — 진행자의 실패담이 핵심

영상 3편 중 마지막 편이 가장 값지다. "내가 이렇게 하다 망했다"가 그대로 나오기 때문이다. 이 원칙들은 그록봇 얘기가 아니라 멀티 에이전트 설계 일반론이라 그대로 이식된다.

원칙 1 — 카테고리로 묶지 마라. 실무 최소 단위로 쪼개라

실패: 메타 광고 계정 전체를 봇 하나에 물려 "모든 캠페인 요약 리포트"를 시켰다. → A 캠페인과 B 캠페인이 한 스레드에 섞여 들어와서 읽기가 힘들어짐.

수정: 캠페인별로 봇을 따로 만들고(메타-A광고, 메타-B광고) 각 봇에 담당 캠페인 ID를 명시했다. 결과 — 서로의 영역을 보지 않고, 정보가 완전히 분리되고, 리포트가 명확해짐.

광고는 원래 캠페인끼리 섞어 분석하거나 동시 변경하지 않는다. 실제 업무 단위 = 봇 단위가 맞았다는 뜻.

원칙 2 — 스코프를 문장으로 못박아라

각 봇에게 "너는 이 캠페인만 본다"를 명시하니 서로 침범하지 않았다. 그룹 스레드에서 "CPA를 어떻게 개선할까"라고 한 번 물으면, A봇은 A 캠페인만, B봇은 B 캠페인만 답한다. A봇은 심지어 "B 캠페인 내용은 섞지 않겠다"고 먼저 선언한다.

원칙 3 — 협업이 필요하면 그룹으로 묶어라 (봇을 합치지 말고)

분리하면 두 봇에 같은 걸 시킬 때 불편해진다. 태그(@봇이름)로 컨텍스트를 요약 전달할 수도 있지만 매번 태그하는 게 귀찮다. → 그룹 스레드가 답이다.

[유튜브 팀] 그룹 스레드 — 사용자는 한 마디만 던진다

  사용자: "우리 다음에 작업해야 되는 유튜브 건 뭔지 확인해봐"
     │
     ├─ 콜라보봇 (리더 역할)  : 이메일 스캔 → 노션 조회 → "호스팅어 전용 영상 건"
     │      └─ 스레드 안에 콘텐츠 리서처가 있음을 인지 → 자동 위임
     │
     ├─ 콘텐츠 리서처         : 해당 주제 리서치 시작 → 결과를 콜라보봇에 태그 회신
     │
     ├─ 계약서 리뷰봇         : (지시 없이) 병렬로 계약서 독해
     │      └─ "이 조항 때문에 이건 하면 안 된다" → 리서처에게 통보

     │

진행자의 요약: "각자 생성된 하네스 안에서 컨트랙트를 지키면서 팀워크를 한다." 이게 그록봇의 정점이다.

원칙 4 — Teach Task로 절차를 가르쳐라

API가 없는 대상(에어비앤비, 메타 광고 관리자)은 결국 브라우저 조작이다. VM에 들어가 Teach Task 녹화를 켜고 직접 클릭한다 → 봇이 영상을 분석해 절차를 이해하고 스킬로 저장한다.

실제 사례: 에어비앤비 접속 → 지역 검색 → 인원/날짜 선택 → Guest Favorite 필터 → 매물 클릭 → 캘린더 열어 점유 확인. 이걸 녹화 한 번 하고 나면 "이제부터 지역을 주면 상위 3개 매물의 8월 숙박률을 계산해줘"가 된다.

2-6. 단점 3가지 (그대로 옮기면 안 되는 것들)

  1. 한국어 품질 — 산출물이 한국어라면 Claude/Codex로 한 번 더 돌리라고 진행자가 직접 권고
  2. 진행 상태 불투명 — 작업 중인지 끝났는지 모를 때가 있다. "아직 진행 중이야?"라고 물어야 답함
  3. 불안정 — 리서치 프리뷰 단계. VM 접근 불가, 루틴 생성 실패, 플러그인 접근 장애가 몇 시간 발생한 적 있음

2-7. 진행자의 논지 — "클로드 코드로도 되는데 왜?"

영상마다 달리는 그 댓글에 대한 반박이 마지막 편에 길게 나온다. 요지만 옮기면:

  • 에이전틱 AI를 써본 사람은 전 세계 5% 미만, 채팅만 써본 사람은 20%+
  • 나머지 90%는 배우는 것 자체가 비용인 사람들이다(시술 한 번에 수백만 원 버는 의사에게 "클로드에 스프레드시트 붙여서…"는 팔리지 않는다)
  • 수요가 있다 = 사업성이 있다. 커서·X 팀이 우리보다 AI를 못 써서 이런 걸 만드는 게 아니다
  • 코딩 에이전트는 소프트웨어를 만들 때 최적이고, 그록봇류는 일상 자동화 결과물에 최적이다 — 용도가 다르다
이 논지를 당신 관점으로 번역하면 "터미널을 켜고, 폴더로 들어가고, 스레드를 새로 시작하는" 비용이 자동화 실행마다 붙는 게 CLI의 구조적 약점이다. 당신이 이미 갖고 있는 하네스에서 이 마찰을 없애는 것이 그록봇에서 뽑아낼 실질 가치다. (→ 아이디어 4·8·9)

Teach Task (화면 녹화 → 절차 학습) 동등 기능 없음. 우회 = 1회 수동 수행 후 절차를 SKILL.md로 문서화 진짜 갭 (우회 가능)
갭이 당신에게 갖는 실제 무게 클라우드 VM 갭은 당신 환경에서 절반으로 줄어든다. 이 PC는 라이브 트레이딩 봇 때문에 상시 가동 중이고 워치독까지 붙어 있다. "내 컴퓨터가 꺼져 있어도"라는 그록봇의 최대 셀링포인트가 성립하지 않는 조건이다.
남는 건 포커스 강탈 문제 하나인데, 이건 전용 Chrome 프로필 + 별도 창 격리로 해결 가능하다(아이디어 5).

PART 4도출 아이디어 10 — 우선순위 순

IDEA 01에이전트를 "카테고리"가 아니라 "실무 최소 단위"로 재편A · 즉시

당신의 하네스는 스킬 54개 + 에이전트를 기능 카테고리로 묶어놨다(기획/실행/검증/회고). 그록봇 진행자가 정확히 그렇게 시작했다가 실패했다. 카테고리 묶음은 읽기에는 좋지만 실행 격리에는 나쁘다.

바꿀 것
프로젝트별로 실제 업무 단위 에이전트를 만들고 스코프를 문장으로 못박는다. 예: youtube-collab(협업 제안 메일만), youtube-contract(계약서만), go-signal-audit(신호 로직만, 실행 코드 금지).
스코프 계약 문장 템플릿
너는 X만 담당한다. Y는 절대 읽지도 수정하지도 않는다. Y가 필요하면 @Y담당 에이전트에게 넘긴다.

IDEA 02"선을 넘지 않는다" 계약을 에이전트 프롬프트에 표준 삽입A · 즉시

그룹 스레드 데모에서 가장 인상적인 장면은 협업이 아니라 인보이스봇이 스스로 멈춘 것이다 — "PDF는 만들지만 네가 승인하기 전엔 메일을 보내지 않을게."

표준 문구 (모든 외부 영향 에이전트에 삽입)
산출물은 만들되, 외부로 나가는 행위(메일 발송·결제·게시·푸시·주문)는 절대 스스로 실행하지 않는다. 준비 완료 상태로 만들고 승인을 요청한다.
왜 당신에게 중요한가
이 머신에는 자금 직결 코드가 돌아간다. 하네스에 이미 HITL 규칙이 있지만 에이전트 프롬프트 레벨의 자기 선언은 별개의 방어층이다. 규칙 파일은 로드 안 되면 그만이고, 프롬프트 문장은 그 에이전트가 사는 한 항상 붙어 있다.
IDEA 03Teach Task 대체 — "1회 수행 → SKILL.md 자동 생성" 루프A · 갭 메우기

그록봇은 녹화로 절차를 배운다. Claude에는 그게 없다. 하지만 절차를 텍스트로 고정하면 동등한 결과가 나오고, 오히려 diff·리뷰·버전관리가 된다.

루프
① Claude in Chrome으로 목표 작업을 한 번 수동 유도 수행 → ② 그 세션에게 절차를 스킬 문서로 뽑게 함 → ③ 다음부터는 변수만 바꿔 스킬 호출.
② 단계 프롬프트
방금 우리가 브라우저에서 수행한 작업을 재사용 가능한 스킬로 문서화해줘.

형식: ~/.claude/skills/<이름>/SKILL.md
포함할 것:
- 입력 변수 (내가 매번 바꿔서 넣을 값들)
- 단계별 조작 순서 (셀렉터/버튼 텍스트/대기 조건 명시)
- 각 단계의 실패 신호와 복구 방법
- 출력 스키마 (어떤 필드를 어디에 저장하는지)
- 절대 하지 말 것 (결제·삭제·설정 변경 등)

추측으로 채우지 말고, 실제로 우리가 거친 단계만 적어줘.
확인 못 한 부분은 "미확인"으로 표기해.
보너스
"추측 금지 / 미확인 표기"가 핵심이다. 이게 없으면 실행 안 해본 단계를 그럴듯하게 지어낸다.

IDEA 05포커스 강탈 없는 브라우저 자동화 — 전용 프로필 격리A · 갭 메우기

IDEA 08그록봇 단점 2번을 선제 차단 — 하트비트 상태 파일B · 품질

각 에이전트는 자기 담당 밖의 판단을 하지 않는다.
