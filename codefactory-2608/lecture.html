디자인 스킬과 그래프 엔지니어링

Claude /design 으로 디자인 시스템 전체를 한 컨텍스트에서 굴리는 법, 그리고 에이전트 워크플로를 노드·엣지로 설계하는 법.

한 줄 요약 — Claude Design(웹)이 로컬 Claude Code 안으로 들어왔다. 결과물이 "고칠 수 없는 LLM 출력물"이 아니라 직접 편집 가능한 아티팩트로 나오고, 웹 → 소셜 → 인쇄물이 하나의 컨텍스트에서 브랜드를 물려받으며 이어진다.

1. 무엇이 달라졌나

기존 문제는 명확했다. LLM에게 디자인을 시키면 결과가 덩어리로 나온다. 마음에 안 드는 부분이 생기면 "세 번째 카드의 모서리를 더 둥글게, 제목은 굵게" 같은 말을 다시 프롬프트로 적어야 했다. 매번 자연어로 왕복하는 이터레이션이 비효율의 본체였다.

/design 스킬은 그 왕복을 없앤다. 산출물이 아티팩트로 열리고, 각 섹션과 프로퍼티가 선택 가능한 객체가 된다.

아티팩트에서 직접 되는 것

  • 더블클릭으로 텍스트 편집 · 볼드 전환 · 문구 추가
  • 색상, 폰트 크기, 아이콘 교체
  • row / column 구조 변경, border-radius 조정
  • 특정 영역에 코멘트를 달고 그대로 Claude에게 넘겨 수정 지시
  • 링크 공유 — 그대로 클라이언트에게 보내 컨펌받기

피그마·페이퍼에서 하던 직접 조작을, Claude Code를 떠나지 않고 한다.

핵심 전환 "디자인은 Claude Design 웹에서 하고, 구현은 Claude Code로 끌고 온다"는 두 도구 왕복이 사라진다. 디자인 → 컨펌 → 구현이 한 세션 안에서 끊기지 않는다.

2. 표준 작업 순서

  1. 최신 버전으로 업데이트 후 /design 호출 슬래시 메뉴에 design 이 보이면 준비 완료. 웹 디자인 전용이 아니다 — 포스터, 소셜 게시물, PPT 모두 대상.
  2. 스킬이 던지는 질문에 성실히 답한다 Anthropic 공식 스킬은 질문 설계가 촘촘하다. 대충 넘기지 말고 스텝을 따르는 편이 결과가 좋다. 예: "애플 기기 리셀링 스토어", "색채 미정 → 시안 3개 먼저 뽑아줘".
  3. 시안 3개 중 방향 선택 색·톤·레이아웃 성향을 여기서 못박는다. 이후 모든 산출물이 이 결정을 상속한다.
  4. 와이어프레임 단계에서 구조를 확정 스킬은 초기에 실제 이미지를 생성하지 않고 와이어프레임 형태로 빠르게 뽑는다. 구조가 틀렸는데 예쁜 이미지를 뽑아놓으면 되돌리기 비싸다 — 의도된 순서다.
  5. 코멘트로 국소 수정, 직접 편집으로 디테일 수정 "이 영역 이렇게 바꿔"는 코멘트 → Claude. "이 글자만 굵게"는 손으로. 둘을 섞는 게 가장 빠르다.
  6. 같은 컨텍스트에서 파생 산출물 요청 여기가 진짜 가치 구간. 다음 절.

3. 진짜 가치는 컨텍스트 승계다

영상의 시연 순서는 웹사이트 → 인스타그램 소셜 세트 → 인쇄물이었다. 두 번째부터는 아무것도 첨부하지 않았다. 앞의 아티팩트가 이미 컨텍스트 안에 있기 때문이다.

Claude가 스스로 "브랜드는 1번 캔버스에서 정한 그대로 씁니다"라고 선언하고 컬러·타이포그래피·스타일을 유지한 채 소셜 세트를 만들었다. 산출 규격도 알아서 다양화했다.

단계산출물승계되는 것
1. 웹홈 · 상품목록(필터) · 상품상세 · 장바구니 · 주문 · 모바일 · 디자인 컴포넌트—
2. 소셜정사각형 · 숏폼 규격 · 배너 · OG 이미지브랜드 컬러, 타이포, 스타일, 1단계에서 손으로 고친 디테일까지
3. 인쇄물포스터 등 프린트 규격1·2단계 누적 전부
놓치기 쉬운 포인트 1·2단계에서 수동으로 다듬은 수정 사항까지 다음 산출물에 반영된다. 즉 취향을 점진적으로 주입할수록 뒤로 갈수록 정확해진다. 첫 판을 대충 넘기면 그 대충함도 함께 상속된다.

각 아티팩트는 독립적으로 열린다. 웹 디자인 보다가 소셜만 따로 열어보는 게 가능하고, 시키지 않아도 에이전틱하게 자체 검증을 돌린다.

4. 구현으로 넘기기

디자인 아티팩트 전체가 레퍼런스이자 컨텍스트다. 여기서 바로 구현을 요청하면 된다.

  • Next.js, 바닐라 JS + CSS + HTML — 스택 무관하게 동일 산출물로 옮길 수 있다
  • 디자인 컴포넌트 목록이 이미 정리돼 있으므로 컴포넌트 단위 구현 지시가 자연스럽다
  • 이미지 생성·영상 도구를 섞으면 완성도가 더 올라간다 (영상에서는 외부 이미지 생성 도구 병행을 언급)
실무 플로우 제안 디자인 아티팩트 링크를 먼저 클라이언트에게 보내 컨펌받고, 승인 난 뒤에 구현을 시작하는 순서가 이제 자연스럽게 성립한다. 구현 후 "이거 아닌데요"를 구조적으로 차단하는 게 이 기능의 실질 효용이다.

5. 모델과 effort

영상 진행자는 평소 high effort를 선호하지만, 이 시연은 medium으로 진행했다. 이유는 명확하다 — 디자인 품질 자체가 이미 충분히 높아서 effort를 올릴 실익이 크지 않고, 속도가 더 중요했다.

권장 구조 잡는 초기 시안은 medium으로 빠르게 여러 장 → 방향 확정 후 디테일 구간에서만 high.

6. 바로 쓰는 프롬프트

1) 초기 호출

/design

애플 기기 리셀링 스토어 웹사이트를 디자인해줘.
색채는 아직 정해진 게 없으니 서로 뚜렷하게 다른 시안 3개를 먼저 만들어줘.
각 시안은 브랜드 톤을 한 줄로 설명해줘.

2) 화면 확장

C안으로 확정할게.
이 방향으로 홈 / 상품목록(필터 포함) / 상품상세 / 장바구니 / 주문완료
5개 화면과 모바일 대응, 그리고 사용된 디자인 컴포넌트 목록을 만들어줘.
이미지는 실제 생성하지 말고 와이어프레임으로 빠르게 진행해줘.

3) 파생 산출물 (컨텍스트 승계 지시)

앞에서 확정한 브랜드 컬러와 타이포그래피를 그대로 유지한 채,
인스타그램 소셜 소재 한 세트를 정적으로 만들어줘.
정사각형 / 숏폼 / 배너 / OG 이미지 규격을 모두 포함해줘.
새로 색을 정하지 말고 1번 캔버스 기준을 따라줘.

4) 구현 이관

지금까지 만든 디자인 아티팩트를 기준으로,
바닐라 HTML + CSS + JS로 홈과 상품목록 화면을 구현해줘.
디자인 컴포넌트 목록에 정의된 이름을 그대로 클래스명으로 써줘.
아티팩트에서 내가 수동으로 수정한 부분도 전부 반영해줘.

7. 1페이지 체크리스트

  • 시안 단계에서 방향을 확정했는가 (뒤로 갈수록 되돌리기 비싸다)
  • 와이어프레임에서 구조를 먼저 확정했는가
  • 파생 산출물 요청 시 "이전 브랜드 기준을 유지하라"를 명시했는가
  • 수동 수정을 충분히 넣은 뒤에 다음 단계로 넘어갔는가
  • 구현 전에 아티팩트 링크로 컨펌을 받았는가

한 줄 요약 — 노드는 독립 에이전트, 엣지는 상태 전달. 파이프라인 하나를 먼저 검증하고 그것을 팬아웃으로 복제한다. 모든 노드에 LLM을 붙이지 않는다. 검증은 코드로 한다.

1. 그래프 엔지니어링이란

AI 에이전트 워크플로를 노드(작업 단위) + 엣지(상태 전달)로 설계하는 기법. 각 노드는 독립된 에이전트로 간주하고, 노드 사이에는 파일로 상태를 넘긴다. 실제 그래프를 API 위에 구현하면 에이전트끼리 메모리를 공유하지 않기 때문에 상태를 명시적으로 전달해야만 한다.

전제 조건 이 기법은 Claude Code / Codex 같은 대화형 환경을 위한 것이 아니다. 그런 환경에서는 ultracode·다이나믹 워크플로가 그래프를 자동으로 만들어준다. 수동 그래프 설계는 API로 독립 에이전트를 직접 띄워 운영할 때 의미가 있다. (아래 실습은 학습 목적으로 익숙한 환경에서 각 스텝을 "독립 에이전트라고 가정"하고 진행한다.)

2. 다섯 가지 설계 원칙

  1. 파이프라인 하나를 먼저 끝까지 검증한다 병렬 구조를 만들면서 동시에 실행하면 토큰이 폭발하고 시간이 오래 걸린다. 한 지역(강남구)만으로 end-to-end를 통과시킨 다음, 그것을 3개로 확장한다.
  2. 모든 노드에 LLM을 붙이지 않는다 환경 설정처럼 결정론적인 작업은 스크립트가 더 싸고 빠르고 재현 가능하다. 영상에서도 "귀찮아서 LLM에 시켰지만, 토큰을 아끼려면 스크립트로 만들어 실행하는 게 훨씬 효율적"이라고 명시한다.
  3. 상태 저장 레이아웃을 먼저 정한다 markdown/ 정리된 상태 · raw/ 원본 응답 · logs/ 실행 기록. raw를 보존해야 다음 노드가 틀렸을 때 처음부터 다시 돌리지 않고 raw를 참조해 재시도할 수 있다.
  4. 검증은 "LLM에게 판단시키기"가 아니라 "검증 코드를 작성해 실행하기" JSON 스키마·조건 충족 검사는 LLM이 필요 없다. 한 번 만들어두면 병렬 노드 N개에 그대로 재사용된다. 이게 확장의 열쇠다.
  5. 팬아웃·팬인·휴먼 인 더 루프의 위치를 명시적으로 정한다 병렬이 유리한 구간은 팬아웃, 하나의 컨텍스트로 판단해야 하는 구간은 팬인. 사람이 승인해야 하는 지점(결제·발송·계약)에 HITL 노드를 넣는다.

4. 노드별 상세

① 환경 설정

고유한 run_id를 만들고 세 폴더를 만든다. 조건(지역·날짜·인원·평점 하한)을 상태 파일로 고정한다. 이 노드는 완전히 결정론적이므로 실전에서는 셸/파이썬 스크립트로 대체하는 게 맞다.

이번 Airbnb 리서치 실행을 위한 고유한 run_id를 만들어줘.
run_id 하위에 markdown/ , raw/ , logs/ 세 폴더를 생성해줘.
- markdown/ : 정리된 상태 (사람이 읽는 설명 + JSON 병기)
- raw/      : 스크래핑 원본 응답 전체
- logs/     : 실행 기록

리서치 조건:
- 지역: 강남구, 마포구, 종로구
- 체크인/아웃: 2026-09-24 ~ 2026-09-26
- 인원: 2명
- 평점: 4.5 이상

조건을 markdown/ 아래 상태 파일로 저장하고 경로만 알려줘.

② 파일럿 리서치 — 스크래핑 레이어가 필요한 이유

추천을 만들려면 실제 웹 데이터가 안정적으로 들어와야 한다. 동적 렌더링, 지역별 결과 차이, 접근 차단 — 이걸 에이전트가 직접 처리하게 두면 깨진다. 더 결정적인 문제는 API로 띄운 독립 에이전트에게는 브라우저가 없다는 점이다.

영상은 이 레이어로 Oxylabs Web Scraper API를 사용한다(영상 스폰서). 렌더링·프록시·결과 반환을 API 한 번으로 처리하고, 요청 시점의 실시간 데이터를 반환한다.

브라우저 자동화 직접 제어스크래핑 API 레이어
에이전트마다 브라우저 필요 — API 환경에서 불가HTTP 요청 하나. 에이전트 수 무관
병렬 3개도 자원 경합. 100개는 비현실적100~200 병렬도 무리 없음
한 곳이 막히면 세션 오염 전파완전 독립 — 실패 노드만 리트라이
요청 지역 고정요청 국가·지역 지정 가능 (항공권처럼 지역별 가격 차가 있는 대상에 유리)

파일럿 리서치 프롬프트

다음 입력 파일을 읽어줘: markdown/<run_id>/conditions.md

강남구 한 지역만 Oxylabs 실제 API로 검색해줘.
더미 데이터나 임의로 만든 숙소는 절대 사용하지 마.

각 숙소에 대해 다음 값으로 정리해줘:
listing_id / 이름 / 지역 / 1박 가격 / 평점 / 리뷰수 / 링크

- 원본 응답 전체는 raw/ 에 그대로 저장
- 정리된 결과는 markdown/ 에 JSON 포함해서 저장
- 실행 기록은 logs/ 에 저장

완료되면 생성한 파일 경로와 숙소 개수만 알려줘.
프롬프트 3대 방어 장치 ① "더미 데이터 금지" — 할루시네이션 차단. ② 출력 스키마 명시 — 안 정하면 매번 제 마음대로 만든다. ③ 저장 경로 지정 — 상태가 다음 노드로 넘어가려면 위치가 고정돼야 한다.

③ 검증 노드 — 이 실습의 핵심

눈으로 확인하는 건 자동화가 아니다. 매 실행마다 사람이 컨펌할 수 없다. 그래서 검증하는 코드를 작성하게 하고, 그 코드를 실행한다.

다음 파일을 프로그램적으로 검증하는 코드를 작성해줘.
(LLM이 읽고 판단하는 방식 말고, 실행 가능한 검증 스크립트로)

검증 항목:
- 파일 존재 여부
- JSON 파싱 성공 여부
- district 가 모두 "강남구" 인지
- listing_id / 가격 / 평점 / 링크 필드 누락 없는지
- 평점이 모두 4.5 이상인지
- 링크가 유효한 형식인지

결과는 PASS / FAIL 로 출력하고 logs/ 에 저장해줘.
작성 후 실제 결과 파일에 대해 실행해서 결과를 알려줘.

영상에서는 Claude가 파이썬을 선택했다. 데이터 검증은 파이썬 쪽이 코드가 간결하다. 이 한 번의 산출물이 이후 모든 병렬 노드에서 재사용된다.

④ 팬아웃 — 서브에이전트 병렬

메인 에이전트가 아래 3개의 독립적인 서브에이전트를 생성하고 병렬로 실행해줘.
- region-강남
- region-마포
- region-종로

각 에이전트는 지정된 지역 하나만 Oxylabs로 조사하고,
출력은 이미 만들어둔 markdown/ 구조에 지역별로 분리 저장해.
서로의 결과를 참조하지 마.
모든 작업이 끝나면 지역별 파일 경로와 숙소 개수를 리포트해줘.

⑤ 병렬 검증 → ⑥ 팬인

③에서 만든 검증 코드를 그대로 3개 결과에 각각 돌린다. 통과분만 하나로 병합한다. 병렬을 나누는 것을 팬아웃, 다시 하나로 모으는 것을 팬인이라 부른다.

⑦ 추천 — 여기가 LLM 구간

다음 두 파일만 읽어줘: (병합 결과 md, 검증 결과 md)
인터넷을 다시 검색하지 말고, 제공되지 않은 정보를 추천하지 마.

검증 통과한 후보 중 3개를 추천해줘.
각 추천에 포함할 내용: 순위 / listing_id / 지역 / 가격 / 평점 / 리뷰수 / 추천 사유

결과를 markdown/<run_id>/recommendations.md 에 저장해줘.

"인터넷 재검색 금지 · 제공되지 않은 정보 추천 금지"가 팬인 노드의 핵심 가드다. 여기서 새 데이터를 끌어오면 앞의 검증이 전부 무의미해진다.

⑧ 결과 검증 → ⑨ 휴먼 인 더 루프

추천도 검증한다(추천이 정확히 3개인지, 모든 필드가 채워졌는지 등). 통과한 경우에만 승인 요청을 만든다.

HITL 위치 설계 이 실습은 결제를 하지 않으므로 승인이 그래프의 마지막이다. 결제·예약 노드를 붙인다면 승인은 그래프 중간으로 이동한다. 거절하거나 수정 요청하면 "이 조건 때문에 제외" 같은 상태를 추가해 그래프를 처음부터 다시 돌릴 수 있다.

5. 그래프 설계 7단계 요약

  1. 만들 그래프의 전체 구성을 먼저 그린다
  2. 파이프라인 하나만 직접 만들어 end-to-end 테스트한다
  3. 검증되면 각 스텝을 에이전트 노드로 분해한다
  4. 병렬 가능한 구간에 독립 실행 가능한 툴/API를 제공한다 (브라우저 직접 제어 금지)
  5. 팬아웃 → 병렬 검증 → 팬인 순서를 고정한다
  6. 결정론적 구간(환경설정·검증)은 LLM을 빼고 코드로 돌린다
  7. 사람이 승인해야 할 지점에 HITL 노드를 삽입한다

6. 실수 방지 체크리스트
