디자인 스킬과 그래프 엔지니어링

Claude /design 으로 디자인 시스템 전체를 한 컨텍스트에서 굴리는 법, 그리고 에이전트 워크플로를 노드·엣지로 설계하는 법.

한 줄 요약 — Claude Design(웹)이 로컬 Claude Code 안으로 들어왔다. 결과물이 "고칠 수 없는 LLM 출력물"이 아니라 직접 편집 가능한 아티팩트로 나오고, 웹 → 소셜 → 인쇄물이 하나의 컨텍스트에서 브랜드를 물려받으며 이어진다.

쉽게 말하면

예전엔 AI가 만들어준 디자인이 굳어버린 찰흙 덩어리였다. 코 모양이 마음에 안 들면 "코를 좀 더 작게" 하고 말로 설명해서 처음부터 다시 빚어달라고 해야 했다.

/design 은 그걸 레고로 바꿨다. 블록 하나만 빼서 다른 색으로 끼우면 끝이다. 그리고 두 번째 작품을 만들 때 첫 작품에 쓴 색깔 통을 그대로 들고 간다.

1. 무엇이 달라졌나

아티팩트에서 직접 되는 것

  • 더블클릭으로 텍스트 편집 · 볼드 전환 · 문구 추가
  • 색상, 폰트 크기, 아이콘 교체
  • row / column 구조 변경, border-radius 조정
  • 특정 영역에 코멘트를 달고 그대로 Claude에게 넘겨 수정 지시
  • 링크 공유 — 그대로 클라이언트에게 보내 컨펌받기

피그마·페이퍼에서 하던 직접 조작을, Claude Code를 떠나지 않고 한다.

2. 진짜 가치는 컨텍스트 승계다

놓치기 쉬운 포인트 1·2단계에서 수동으로 다듬은 수정 사항까지 다음 산출물에 반영된다. 취향을 점진적으로 주입할수록 뒤로 갈수록 정확해진다.

3. 표준 작업 순서

  1. 최신 버전으로 업데이트 후 /design 호출 웹 디자인 전용이 아니다 — 포스터, 소셜 게시물, PPT 모두 대상.
  2. 스킬이 던지는 질문에 성실히 답한다 Anthropic 공식 스킬은 질문 설계가 촘촘하다. 예: "애플 기기 리셀링 스토어", "색채 미정 → 시안 3개 먼저".
  3. 시안 3개 중 방향 선택 색·톤·레이아웃 성향을 여기서 못박는다. 이후 모든 산출물이 이 결정을 상속한다.
  4. 와이어프레임 단계에서 구조를 확정 초기에는 실제 이미지를 생성하지 않고 와이어프레임으로 빠르게 뽑는다. 구조가 틀렸는데 예쁜 이미지를 뽑아두면 되돌리기 비싸다 — 의도된 순서다.
  5. 코멘트로 국소 수정, 직접 편집으로 디테일 수정 "이 영역 이렇게 바꿔"는 코멘트 → Claude. "이 글자만 굵게"는 손으로. 둘을 섞는 게 가장 빠르다.
  6. 같은 컨텍스트에서 파생 산출물 요청 여기가 진짜 가치 구간. 위 도식 참조.

4. 구현으로 넘기기

디자인 아티팩트 전체가 레퍼런스이자 컨텍스트다. 여기서 바로 구현을 요청하면 된다.

  • Next.js, 바닐라 JS + CSS + HTML — 스택 무관하게 동일 산출물로 옮길 수 있다
  • 디자인 컴포넌트 목록이 이미 정리돼 있으므로 컴포넌트 단위 구현 지시가 자연스럽다
  • 이미지 생성·영상 도구를 섞으면 완성도가 더 올라간다
실무 플로우 디자인 아티팩트 링크를 먼저 클라이언트에게 보내 컨펌받고, 승인 난 뒤에 구현을 시작한다. 구현 후 "이거 아닌데요"를 구조적으로 차단하는 게 이 기능의 실질 효용이다.

5. 바로 쓰는 프롬프트

1) 초기 호출

/design

애플 기기 리셀링 스토어 웹사이트를 디자인해줘.
색채는 아직 정해진 게 없으니 서로 뚜렷하게 다른 시안 3개를 먼저 만들어줘.
각 시안은 브랜드 톤을 한 줄로 설명해줘.

2) 화면 확장

C안으로 확정할게.

5개 화면과 모바일 대응, 그리고 사용된 디자인 컴포넌트 목록을 만들어줘.
이미지는 실제 생성하지 말고 와이어프레임으로 빠르게 진행해줘.

3) 파생 산출물 — 컨텍스트 승계 지시

앞에서 확정한 브랜드 컬러와 타이포그래피를 그대로 유지한 채,
인스타그램 소셜 소재 한 세트를 정적으로 만들어줘.
정사각형 / 숏폼 / 배너 / OG 이미지 규격을 모두 포함해줘.
새로 색을 정하지 말고 1번 캔버스 기준을 따라줘.

4) 구현 이관

지금까지 만든 디자인 아티팩트를 기준으로,
바닐라 HTML + CSS + JS로 홈과 상품목록 화면을 구현해줘.
디자인 컴포넌트 목록에 정의된 이름을 그대로 클래스명으로 써줘.
아티팩트에서 내가 수동으로 수정한 부분도 전부 반영해줘.

  • 수동 수정을 충분히 넣은 뒤에 다음 단계로 넘어갔는가

한 줄 요약 — 노드는 독립 에이전트, 엣지는 상태 전달. 파이프라인 하나를 먼저 검증하고 그것을 팬아웃으로 복제한다. 모든 노드에 LLM을 붙이지 않는다. 검증은 코드로 한다.

쉽게 말하면 — 김밥 공장

김밥을 300줄 만들어야 한다. 처음부터 작업대 3개를 동시에 돌리면, 뭐가 잘못됐을 때 어느 작업대가 범인인지 모른다. 그래서 먼저 한 줄만 끝까지 만들어본다. 그게 통과하면 그때 작업대를 늘린다.

전제 조건 이 기법은 Claude Code / Codex 같은 대화형 환경을 위한 것이 아니다. 그런 환경에서는 ultracode·다이나믹 워크플로가 그래프를 자동으로 만들어준다. 수동 그래프 설계는 API로 독립 에이전트를 직접 띄워 운영할 때 의미가 있다.

1. 그래프를 직접 돌려보기

아래 도식은 클릭·재생이 되는 그래프다. 노드를 누르면 그 노드가 무슨 일을 하고, 왜 LLM을 붙였는지 혹은 안 붙였는지가 아래에 나온다. 비용 렌즈를 켜면 어느 노드가 실제로 돈을 쓰는지 한눈에 보인다.

2. 다섯 가지 설계 원칙

  1. 파이프라인 하나를 먼저 끝까지 검증한다 병렬 구조를 만들면서 동시에 실행하면 토큰이 폭발하고 시간이 오래 걸린다. 한 지역(강남구)만으로 end-to-end를 통과시킨 다음 3개로 확장한다.
  2. 모든 노드에 LLM을 붙이지 않는다 환경 설정처럼 결정론적인 작업은 스크립트가 더 싸고 빠르고 재현 가능하다. 영상도 "귀찮아서 LLM에 시켰지만, 토큰을 아끼려면 스크립트가 훨씬 효율적"이라고 명시한다.
  3. 상태 저장 레이아웃을 먼저 정한다 markdown/ 정리된 상태 · raw/ 원본 응답 · logs/ 실행 기록. raw를 보존해야 다음 노드가 틀렸을 때 처음부터 다시 돌리지 않는다.
  4. 검증은 "LLM에게 판단시키기"가 아니라 "검증 코드를 작성해 실행하기" JSON 스키마·조건 충족 검사는 LLM이 필요 없다. 한 번 만들어두면 병렬 노드 N개에 그대로 재사용된다. 이게 확장의 열쇠다.
  5. 팬아웃·팬인·휴먼 인 더 루프의 위치를 명시적으로 정한다 병렬이 유리한 구간은 팬아웃, 하나의 컨텍스트로 판단해야 하는 구간은 팬인. 사람이 승인해야 하는 지점(결제·발송·계약)에 HITL을 넣는다.

3. 왜 브라우저가 아니라 API 레이어인가

영상 기준 사용된 도구는 Oxylabs Web Scraper API(해당 영상 스폰서)다. 렌더링·프록시·결과 반환을 API 한 번으로 처리하고 요청 국가·지역까지 지정할 수 있어, 항공권처럼 지역별 가격 차가 있는 대상에 유리하다.

4. 노드별 프롬프트

① 환경 설정

이번 Airbnb 리서치 실행을 위한 고유한 run_id를 만들어줘.
run_id 하위에 markdown/ , raw/ , logs/ 세 폴더를 생성해줘.
- markdown/ : 정리된 상태 (사람이 읽는 설명 + JSON 병기)
- raw/      : 스크래핑 원본 응답 전체
- logs/     : 실행 기록

리서치 조건:
- 지역: 강남구, 마포구, 종로구
- 체크인/아웃: 2026-09-24 ~ 2026-09-26
- 인원: 2명
- 평점: 4.5 이상

조건을 markdown/ 아래 상태 파일로 저장하고 경로만 알려줘.

② 파일럿 리서치

다음 입력 파일을 읽어줘: markdown/<run_id>/conditions.md

강남구 한 지역만 실제 스크래핑 API로 검색해줘.
더미 데이터나 임의로 만든 숙소는 절대 사용하지 마.

각 숙소에 대해 다음 값으로 정리해줘:
listing_id / 이름 / 지역 / 1박 가격 / 평점 / 리뷰수 / 링크

- 원본 응답 전체는 raw/ 에 그대로 저장
- 정리된 결과는 markdown/ 에 JSON 포함해서 저장
- 실행 기록은 logs/ 에 저장

완료되면 생성한 파일 경로와 숙소 개수만 알려줘.
프롬프트 3대 방어 장치 ① "더미 데이터 금지" — 할루시네이션 차단. ② 출력 스키마 명시 — 안 정하면 매번 제 마음대로 만든다. ③ 저장 경로 지정 — 상태가 다음 노드로 넘어가려면 위치가 고정돼야 한다.

③ 검증 코드 — 이 실습의 핵심

다음 파일을 프로그램적으로 검증하는 코드를 작성해줘.
(LLM이 읽고 판단하는 방식 말고, 실행 가능한 검증 스크립트로)

검증 항목:
- 파일 존재 여부
- JSON 파싱 성공 여부
- district 가 모두 "강남구" 인지
- listing_id / 가격 / 평점 / 링크 필드 누락 없는지
- 평점이 모두 4.5 이상인지
- 링크가 유효한 형식인지

결과는 PASS / FAIL 로 출력하고 logs/ 에 저장해줘.
작성 후 실제 결과 파일에 대해 실행해서 결과를 알려줘.

④ 팬아웃

메인 에이전트가 아래 3개의 독립적인 서브에이전트를 생성하고 병렬로 실행해줘.
- region-강남
- region-마포
- region-종로

각 에이전트는 지정된 지역 하나만 조사하고,
출력은 이미 만들어둔 markdown/ 구조에 지역별로 분리 저장해.
서로의 결과를 참조하지 마.
모든 작업이 끝나면 지역별 파일 경로와 숙소 개수를 리포트해줘.

⑦ 팬인 후 추천 — 유일한 LLM 구간

다음 두 파일만 읽어줘: (병합 결과 md, 검증 결과 md)
인터넷을 다시 검색하지 말고, 제공되지 않은 정보를 추천하지 마.

검증 통과한 후보 중 3개를 추천해줘.
각 추천에 포함할 내용: 순위 / listing_id / 지역 / 가격 / 평점 / 리뷰수 / 추천 사유

결과를 markdown/<run_id>/recommendations.md 에 저장해줘.

"인터넷 재검색 금지 · 제공되지 않은 정보 추천 금지"가 팬인 노드의 핵심 가드다. 여기서 새 데이터를 끌어오면 앞의 검증이 전부 무의미해진다.

5. 실수 방지 체크리스트

안티패턴증상대응
처음부터 병렬 구축토큰 폭발, 디버깅 불가파일럿 1개 통과 후 확장
모든 노드에 LLM비용·지연 누적, 결과 비결정적환경설정·검증은 스크립트
raw 응답 미보존노드 하나 실패에 전체 재실행raw/ 항상 저장, 다음 노드가 참조
LLM에게 검증 판단 위임매번 결과가 다름, 재사용 불가검증 코드를 생성해 실행
출력 스키마 미지정노드 간 상태 포맷 불일치필드명까지 프롬프트에 명시
브라우저를 노드가 직접 제어API 환경에서 아예 불가, 병렬 실패스크래핑 API 레이어로 추상화
팬인에서 재검색 허용검증되지 않은 데이터가 결론에 유입"재검색 금지" 가드 문구

그래프 설계 7단계

  1. 만들 그래프의 전체 구성을 먼저 그린다
  2. 파이프라인 하나만 직접 만들어 end-to-end 테스트한다
  3. 검증되면 각 스텝을 에이전트 노드로 분해한다
  4. 병렬 가능한 구간에 독립 실행 가능한 툴/API를 제공한다
  5. 팬아웃 → 병렬 검증 → 팬인 순서를 고정한다
  6. 결정론적 구간(환경설정·검증)은 LLM을 빼고 코드로 돌린다
  7. 사람이 승인해야 할 지점에 HITL 노드를 삽입한다
