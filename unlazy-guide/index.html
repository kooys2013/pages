Chapter 01 · 문제의 정체

게으름의 두 얼굴

모델이 게을러지는 방식은 정확히 두 가지다. 그리고 둘 중 하나는 훨씬 위험하다.

얼굴 ① — 안 끝났는데 "다 했다"

파일 여러 개를 검토하라고 시키면 몇 개만 열어보고 "전부 확인했다"고 보고한다. 일찍 멈추는 것 자체는 봐줄 수 있다. 문제는 일찍 멈추고도 다 끝냈다고 말하는 것이다. 검증 없이 그 위에 다음 작업을 쌓으면 부실 공사가 된다.

얼굴 ② — 조용한 범위 축소

다섯 부분짜리 작업을 시키면 쉬운 네 개만 만들고 어려운 하나는 건너뛴다. 마지막 요약에는 빠진 게 있다는 언급 자체가 없다. 사용자가 직접 세어보기 전까지 모른다.

왜 이러나 — 원인은 기억 구조

모델에는 내장 기억이 없다. 이전 대화를 "기억"하는 것처럼 보이는 이유는, 에이전트가 매번 지금까지의 모든 메시지를 새 프롬프트에 통째로 붙여 재전송하기 때문이다. 대화가 길어질수록 그 더미가 커지고, 모델이 한 번에 주의를 기울여야 할 대상이 늘어난다.

새 세션 시작
집중 온전
중반
분산 시작
긴 세션 후반
80% 스톨

그래서 새 컨텍스트에서는 멀쩡하던 에이전트가 긴 세션 후반에 무너진다. 스킬 원문은 이를 "stall-at-80-percent는 긴 컨텍스트 말기의 질병"이라 부른다. Opus든 GPT든 최상위 모델도 예외가 아니고, 작은 모델은 한계가 더 빨리 드러날 뿐이다.

Chapter 02 · 기존 해법 해부

왜 지금까지의 처방은 전부 뚫렸나

완료 강제 장치는 이전에도 있었다. 셋 다 같은 자리에 구멍이 있다.

방식작동구멍

자체 체크리스트 루프태스크 목록에 통과 조건을 달아 검사검사는 실재하지만 채점을 에이전트 본인이 한다
공통 구멍 하나로 요약

"끝났는가"를 결정하는 주체가 결국 에이전트 자신이다. 그리고 셋 다 컨텍스트가 신선할 땐 잘 작동하다가, 정작 버텨줘야 할 긴 세션 후반에 무너진다.

Unlazy 실행의 첫 축. 작업을 나무처럼 N층으로 분해하고, 실제 일은 맨 끝 잎(leaf)에서만 일어난다.

2

Chapter 04 · 구조 ②

Gates 원장 — 완료는 말이 아니라 명령어가 정한다

Unlazy의 심장. 일 시작 전에 게이트 파일을 쓰고, 끝났다는 주장은 오직 명령 실행 결과로만 인정된다.

게이트 하나는 네 줄이다. 체크박스 + 결과 정의 + CHECK(실행할 셸 명령) + EXPECT(기대 문자열/정규식) + EVIDENCE(증거, 처음엔 "pending"). 에이전트가 "다 했다"고 주장하면 gate-check.mjs가 CHECK를 직접 실행해서, EXPECT가 출력에 있을 때만 박스를 채우고 실제 출력을 EVIDENCE에 기록한다.

🔒 게이트 원장 체험 — 손으로 체크해 보라
G1 — 빌드가 통과한다
CHECK: npm run build EXPECT: exit 0 EVIDENCE: pending
G2 — 페이지 6개 전부 라우팅된다
CHECK: grep -c "route(" src/app.js EXPECT: 6 EVIDENCE: pending
UNMET — 자가 체크 감지. 박스는 채워졌는데 EVIDENCE가 pending이다. 원장 규칙에서 이건 빈 박스보다 나쁘다: 안 한 일이 아니라 거짓말한 일이 되기 때문. 체크를 되돌린다.
ALL MET (2 of 2) — CHECK 명령이 실행됐고 EXPECT가 매칭됐다. EVIDENCE에 실제 출력이 남았다. 이것만이 완료다.

탈출구도 정직하게 — ABANDON

게이트가 진짜 불가능해지면 조용히 빼는 게 아니라 ABANDON: G2 사유 한 줄을 파일에 남기고 보고서에 명시한다. 도구는 이를 실패가 아닌 정직한 종료로 취급한다. 1장의 "조용한 범위 축소"를 원천 봉쇄하는 장치.

검증 3계층 — 자기인증은 없다

L1
leaf가 자기 게이트를 스스로 실행 — 기본. 하지만 자기 채점이므로 이걸로 끝내지 않는다.
L2
부모(driver)가 같은 CHECK를 재실행 — orchestrated 모드의 존재 이유. leaf가 "통과했다"고 보고해도 부모가 다시 돌려서 다르면 미완료.
L3
Stop 훅 (선택) — 미충족 게이트가 남은 채 턴을 끝내는 것 자체를 구조적으로 차단. 하네스 동작을 바꾸므로 절대 몰래 설치하지 않는 게 스킬 자체 규칙.
보고서는 완료의 분위기(vibe)가 아니라, 원장이 뒷받침하는 주장의 집합이다.unlazy SKILL.md "Report audit" — 보고 직전 모든 숫자 재측정, 아니면 unverified 라벨

Chapter 06 · 문제점

치명적 결함 — 하나씩, 순서대로

영상이 "아주 좋다"면서도 그대로 쓰지 말라고 한 이유. orchestrated 모드의 driver 루프가 직렬이다.

# 원본 v2.0.0 orchestration.md — driver loop
2. Dispatch one leaf. Spawn a fresh subagent with the leaf brief.
   대기 → 검증 → 다음 leaf...

leaf 하나 맡기고, 끝날 때까지 기다리고, 검증하고, 그다음 leaf. Claude Code도 Codex도 서브에이전트를 동시에 여러 개 돌릴 수 있는데 그 능력을 안 쓴다. 문서 말미에 "independent leaves can run as parallel subagents"라는 한 줄이 있긴 하지만 루프 본문이 직렬이라 실제 실행은 직렬로 흘러간다.

실측 피해 (영상 시연)

데모 앱 빌드를 원본 그대로 실행 — 3~4시간 돌리고 얻은 것: 로그인 페이지 한 장. leaf들이 한 줄로 서서 차례를 기다리는 동안 벽시계만 돌았다.

직렬 (원본)
3~4시간
병렬 10 (수정)
약 2시간

같은 2시간이라도 내용물이 다르다 — 직렬은 로그인 페이지, 병렬은 전체 기능이 작동하는 앱. 시간 단축이 아니라 완성 여부의 차이였다.

Chapter 07 · 해결

수정법 — leaf가 아니라 wave를 보낸다

영상의 처방: "스킬 파일을 열어 병렬 서브에이전트를 쓰도록 고쳐라." 우리는 그대로 했고, 커밋으로 남겼다.

# 패치 후 driver loop (~/.claude/skills/unlazy, 커밋 b0aa659)
2. Dispatch a wave, not a leaf. Serial dispatch is the failure
   mode this step exists to kill. Spawn ALL leaves of the current
   wave as parallel subagents in a single message (cap 10).
3. Verify, never trust. As each leaf reports, re-run its checks
   in the driver. Verification stays serial.

wave의 정의 — 아무거나 동시에 던지지 않는다

1
wave = 의존성 층.서로 의존하지 않고, 소유 파일이 겹치지 않는 leaf들의 묶음. PLAN.md에 Waves 표(어느 leaf가 어느 파일을 소유하는지)를 먼저 쓴다.
2
한 메시지에 전부 스폰, 상한 10.영상 실측 구성과 동일. 초과분은 다음 배치로.
3
검증은 절대 병렬화하지 않는다.병렬성이 사는 곳은 실행(벽시계), 신뢰가 사는 곳은 driver의 직렬 재검증. 이 선을 지켜야 속도를 벌면서 4장의 검증 계층이 무너지지 않는다.
4
실패한 leaf가 wave를 막지 않는다.즉시 그 leaf만 재디스패치, 나머지는 계속.
보너스 — 패치 중 원본 버그 추가 발견

gate-check.mjs의 인자 파싱: --timeout 옵션이 없으면 인덱스 계산이 -1+1=0이 되어 첫 번째 파일 인자를 무조건 버린다. 즉 SKILL.md가 안내하는 표준 호출 node gate-check.mjs GATES.md가 그대로 "no gate files found"로 실패. 가드 조건 추가로 수정, smoke test 2게이트 PASS 확인. 영상에도 없는 결함 — 원문을 정독해야 나오는 종류다.

영상의 두 번째 팁 — 모델 라우터

기계적인 leaf(보일러플레이트, 단순 변환)는 싼 모델에게, 설계·통합·검증은 강한 모델에게. 이 티어링은 unlazy 원문 token-economy 규칙에 이미 들어 있고, 우리 하네스의 model-strategy와도 같은 방향이다.

Chapter 08 · 우리 시스템 적용

어디에 끼우고, 무엇과 역할을 나누나

스킬 하나 더 얹은 게 아니라, 기존 검증 체계의 빈 자리에 끼웠다.

Stop 훅은 왜 보류했나

unlazy 동봉 Stop 훅(미충족 게이트로 턴 종료 시 차단)은 설치하지 않았다. 우리 하네스엔 이미 Stop 훅이 여럿 있고, 전역 설치하면 잡담 턴까지 간섭한다. 우리 원칙(fit-escalation-ladder)도 "warn에서 관찰 후 block으로 점진 승격"인데 훅 즉시 설치는 관찰 없이 block부터 도입하는 꼴. 스킬 원문 스스로도 "절대 몰래 설치하지 말라"고 못 박는다. gates 방식이 정착하면 그때 승격 검토.

세 줄 요약

1. AI의 게으름은 기억 구조의 부산물이다 — 컨텍스트가 쌓이면 주의가 희석되고, "다 했다"는 말과 조용한 범위 축소가 나온다. 채점자가 에이전트 자신인 해법은 전부 뚫렸다.

2. Unlazy는 판정권을 회수한다 — 게이트 파일의 CHECK 명령이 실행되고 EXPECT가 매칭되고 EVIDENCE가 기록될 때만 완료다. 체크됐는데 증거가 pending이면 빈 박스보다 나쁘다.

3. 단 원본은 직렬이라 느리다 — leaf가 아니라 wave(파일 소유가 겹치지 않는 의존성 층)를 병렬로 보내도록 고쳐 써라. 실행은 병렬, 검증은 직렬. 그게 3~4시간 로그인 페이지와 2시간 완성 앱의 차이였다.
