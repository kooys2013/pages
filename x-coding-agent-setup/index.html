왜왜 이걸 알아야 하나

이 모듈이 뒤집는 통념 — 좋은 모델을 쓰면 알아서 척척 해줄 거라는 통념 — 실제로는 같은 모델도 역할·규칙·완료 기준을 얼마나 쌓아뒀는지에 따라 결과가 갈린다.

스탠포드 CS146S와 Anthropic Claude Academy가 나란히 가르치는 건 더 이상 '프롬프트 잘 쓰기'가 아니라 에이전트가 일할 환경을 설계하는 법이다. 같은 모델을 쓰는데 결과가 다른 이유도 성능 차이가 아니라, 역할·규칙을 얼마나 쌓아뒀는지의 차이라고 이 모듈의 카드들은 입을 모은다.

그래서 실행 순서가 바뀐다. 요구사항이 애매하면 에이전트가 먼저 캐묻게 만들고(interview-me·Blind Spot Pass), 코딩 전 20분은 설계에 쓰고, 무엇보다 작업 범위·검증 방법·완료된 모습을 미리 정의해줘야 한다. 모호하게 던지면 5.6 Sol 같은 최신 모델일수록 더 오래 헤매고 토큰만 태운다.

이 흐름의 끝은 '프롬프트'가 아니라 '루프'다. 사람이 매번 지시하는 대신 stop 조건까지 반복하는 루프를 설계하고, 그 결과는 Prompt·Context·Harness 세 층으로 한 시스템처럼 관리된다. 새 모델이 나오면 이 세팅(스킬·AGENTS.md·프롬프트)을 다시 점검하라는 것도 같은 맥락이다.

2. AI와 에이전트의 차이는 미리 정한 역할과 규칙
그냥 AI는 길에서 만난 원어민이야. 물어보면 대답은 해주는데 내가 누군지는 몰라. 에이전트는 역할이랑 규칙을 미리 정해둔 AI, 그러니까 내 레벨을 알고 어제 틀린 걸 기억하는 과외 선생님이지. 클로드 프로젝트에 학생 정보 세 줄과 수업 규칙만 붙여넣으면 만들어져. 같은 모델을 쓰는데 누구 AI는 똑똑해 보이는 이유도, 오랫동안 말투·검수 기준 같은 작업규칙을 쌓아뒀기 때문이라고 말해.

🔍 근거와 숫자 — 글쓴이는 자신이 최상위 등급(Sol Ultra)이 아니라 평소 Medium~High 정도로만 쓰는데도 AI가 똑똑해 보이는 이유를 오랫동안 쌓아온 작업규칙 때문이라 말한다. 만드는 법도 학생 정보 세 줄(레벨·목표·하루 공부 시간)과 수업 규칙만 클로드 프로젝트 지침에 붙여넣으면 되고, 무료 계정도 가능하다.

  • 같은 채팅방(프로젝트)에서만 이어서 대화한다 — 새 방을 열면 어제 틀린 걸 다 잊는다

요구가 애매하면 에이전트도 눈치 보며 대충 밀어붙여. interview-me·grilling 스킬은 실행 전에 맥락·목표·제약부터 캐물어. Krongggggg는 Blind Spot Pass(모르는 걸 먼저 찾기)·Reference·Post Quiz 팁을 더하고. The Architect는 코딩 전 20분을 설계에 써서 14개 프로젝트 유형에 맞는 설계도부터 만들게 하는 플러그인이야.

🔍 근거와 숫자 — AI_Caffeine은 interview-me·grilling 두 스킬을 꼽고, Krongggggg는 Blind Spot Pass·Brainstorm+Prototype·Interview·Reference·Implementation Notes·Post Quiz 같은 실전 팁을 정리한다. The Architect 플러그인은 코딩 전 처음 20분 설계를 건너뛰는 것이 실패 원인이라 보고, 14개 주요 프로젝트 유형을 지원한다.

7. Prompt·Context·Harness 세 층
AI_Caffeine의 정리: Prompt는 뭘 할지, Context는 뭘 알아야 하는지, Harness는 얼마나 믿고 돌릴 수 있는지를 정해. Prompt만 잘 써도 최신·충분한 정보는 보장 못 하고, Context를 모아도 검증·복구·평가 없으면 못 믿을 결과가 나와. 망하는 패턴은 목표 흐린 Prompt, 너무 많거나 적은 Context, 검증 없는 Harness. 이 3층을 한 시스템으로 설계하는 능력이 중요해진다는 이야기.

🔍 근거와 숫자 — AI_Caffeine은 Prompt Engineering(뭘 할지)·Context Engineering(뭘 알아야 하는지)·Harness Engineering(agent loop·tool calling·guardrails·error handling·logging·eval·testing·versioning·cost control·monitoring)의 3층 구조를 제시하고, 망하는 패턴을 '목표 흐린 Prompt·과다/과소 Context·검증 없는 Harness'로 요약한다.

🧾 (정리)

⚙️ 당장 적용할 규칙

  • 지시문(Prompt)만 다듬지 말고 무엇을 알아야 하는지(Context)도 같이 설계한다
  • 정보는 많이 넣는 게 아니라 딱 필요한 만큼만 찾고·거르고·압축해서 넣는다
  • agent loop·guardrails·error handling·logging·eval을 Harness 쪽 체크리스트로 따로 관리한다
  • 결과가 못 미더우면 세 층 중 어디가 비어 있는지부터 진단한다 (Prompt/Context/Harness)
  • 새 기능을 붙일 때마다 이 기능이 세 층 중 어디에 속하는지 먼저 분류한다

왜왜 이걸 알아야 하나

이 모듈이 뒤집는 통념 — 많이 넣을수록 AI가 더 잘 안다는 통념을 뒤집는다 — CLAUDE.md 한 장에 다 몰아넣거나 컨텍스트를 끝까지 채우면 오히려 검색 능력이 떨어진다(컨텍스트 부패).

CLAUDE.md 하나에 규칙을 계속 쌓으면 언젠가 문서 한 권이 되고, Agent가 일을 시작하기도 전에 정작 중요한 지침이 수천 줄 사이에 묻힌다. CLAUDE.md·settings.json·rules/·commands/·skills/·agents/·hooks/로 역할을 나누고, 루트 CLAUDE.md는 목표·구조·필수 규칙만 짧게 두는 편이 유지보수에 낫다.

인용된 수치로는(GPT-5.5 데이터 기준이라는 주장) 256k 토큰에서 검색 능력이 80%였다가 100만 토큰으로 늘리면 36%로 떨어진다 — 컨텍스트 창이 커진다고 AI가 그 안에서 더 잘 추론하는 건 아니라는 뜻이다. 그래서 /checkup 같은 정리 루틴이나 skill 수를 줄이는 접근(Waza)이 함께 소개된다.

에이전트가 같은 파일을 계속 열며 토큰을 태우는 문제는 CodeGraph·OpenWiki·CodeFlow 같은 코드 지도 도구로, 세션이 바뀔 때마다 맥락을 다시 설명해야 하는 문제는 ctx·Memanto 같은 기억 레이어로, PDF·Word 같은 자료가 구조를 깨뜨리는 문제는 MarkItDown·AnyDoc·MinerU 같은 Markdown 변환 도구로 각각 풀 수 있다.

8. CLAUDE.md 한 장에서 층 구조로
CLAUDE.md 하나에 컨텍스트를 다 담으면 금방 한계가 온다. CLAUDE.md·settings.json(권한·모델·hooks)·rules/(주제별 규칙)·commands/·skills/(동적 능력)·agents/·hooks/로 역할을 나누면 안정적이다. 루트 CLAUDE.md는 목표·구조·필수 규칙만 짧게 두고, 모듈별 세부 규칙은 해당 폴더 CLAUDE.md에, 반복 작업은 skills로, 필수 규칙은 hooks로 자동 검사하게 옮긴다.

🔍 근거와 숫자 — Claude Code 프로젝트 안에 CLAUDE.md 하나만 덩그러니 두는 방식은 금방 한계가 온다며, 유지보수 가능한 구성은 CLAUDE.md(전체 컨텍스트·기본 규칙)·settings.json(권한·모델·hooks)·rules/(주제별 규칙)·commands/(반복 workflow)·skills/(동적 능력)·agents/(전용 서브 Agent)·hooks/(툴 호출 전후 자동 검증)로 나누는 구성이 소개된다. 아키텍트 Brij Kishore Pandey의 방식은 루트 CLAUDE.md를 짧게(목표·구조·필수 규칙만) 두고, API·DB 같은 모듈 맥락은 해당 폴더 CLAUDE.md에, 반복 작업은 .claude/skills로, 반드시 지켜야 할 규칙은 .claude/hooks로 자동 검사하도록 나누라고 권한다.

🧾 (정리)
이 프로젝트 CLAUDE.md를 목표·구조·필수 규칙만 남기고, API/DB 규칙은 각 폴더 CLAUDE.md로, 반복 작업은 skills로 옮겨줘.

⚙️ 당장 적용할 규칙

  • 루트 CLAUDE.md는 목표·구조·필수 규칙만 짧게 둔다
  • API·DB 등 모듈별 규칙은 해당 폴더 CLAUDE.md에 따로 둔다
  • 반복되는 작업(코드 리뷰·리팩터링·배포)은 skills/로 옮긴다
  • 반드시 지켜야 할 규칙은 hooks/로 자동 검사하게 만든다
  • 권한·모델·hooks 설정은 settings.json에 분리한다

🧪 실습 — 지금 쓰는 CLAUDE.md를 열어 목표·구조·필수 규칙 외의 내용(API 형식, 코드 예시, 반복 절차)을 찾아 표시하고, 그중 하나를 rules/ 또는 skills/ 파일로 옮겨본다. (20분)

9. 많이 넣을수록 못 읽는다: 컨텍스트 부패
다들 100만 토큰 컨텍스트를 자랑하지만 실상은 다르다. 인용된 수치로는 256k 토큰에서 검색 능력이 80%인데, 100만 토큰으로 늘리면 36%로 떨어진다(GPT-5.5 기준이라는 주장, Prime Intellect 엔지니어가 20분짜리 talk에서 소개). 모델이 컨텍스트를 받아들이긴 해도 제대로 추론하지 못하는 현상을 '컨텍스트 부패'라 부른다. 무작정 프롬프트를 늘리는 구조는 버려야 하는데, 이 수치는 재인용된 것이라 출처 확인이 필요하다.

🔍 근거와 숫자 — 에이전트가 긴 대화만 들어가면 바보가 되는 이유로, 100만 토큰 컨텍스트를 지원한다는 스펙 자랑이 사실은 사기극에 가깝다는 주장이 인용된다. Prime Intellect 엔지니어가 20분짜리 talk에서 짚은 수치로는 GPT-5.5 기준 256k 토큰일 때 검색(retrieval) 능력이 80%인데, 100만 토큰으로 늘리면 36%로 떨어진다. 모델이 컨텍스트를 받아들이긴 해도 그 안에서 제대로 추론하지 못하는 현상을 '컨텍스트 부패(context rot)'라 부르며, 계속 학습(continual learning)·자기 트레이스 학습·실제 환경이 해법이라는 주장으로 이어진다.

⚙️ 당장 적용할 규칙

  • '100만 토큰 지원'이라는 스펙만 보고 안심하지 않는다
  • 장문 컨텍스트일수록 검색 능력이 떨어질 수 있다고 가정한다
  • 필요 없는 내용을 계속 쌓지 말고 주기적으로 compact/정리한다
  • 수치(80%→36%)는 인용의 인용이므로 원 출처를 확인하고 참고한다

🧪 실습 — 지금 쓰는 세션의 컨텍스트가 얼마나 쌓였는지 확인하고, 지금 안 쓰는 파일/대화를 compact하거나 새 세션으로 나눠본다. (10분)

10. 주기적으로 치우기: /checkup과 스킬 정리
Claude Code로 헤비하게 작업하다 프롬프트가 꼬이거나 느려지면 /checkup을 실행한다. 안 쓰는 스킬·MCP·플러그인을 정리하고, CLAUDE.md 중복을 제거하고, 루트 CLAUDE.md를 하위 CLAUDE.md·스킬로 쪼개준다. Waza는 겹치는 기능을 걷어내고 자주 터지는 순간마다 하나씩 대응하는 핵심 스킬만 남겼고, Skills Hub는 여러 에이전트에 흩어진 스킬을 한곳에서 태그·활성화·업데이트까지 관리한다.

🔍 근거와 숫자 — Claude Code로 며칠 헤비하게 작업하다 프롬프트가 꼬이거나 속도가 느려질 때 /checkup을 쓰면, 안 쓰는 skills/MCP/plugin을 정리하고 컨텍스트를 아끼며, 로컬 CLAUDE.md를 체크인된 CLAUDE.md와 중복 제거하고, 루트 CLAUDE.md를 하위 CLAUDE.md와 스킬로 쪼개주고, 느린 hook을 끄고, Claude Code를 최신 버전으로 올리고, auto mode를 기본으로 켜고, 자주 거부되는 읽기 전용 명령을 미리 승인해준다(변경 전에는 항상 확인을 거친다). 겹치는 skill을 수백 개씩 쌓는 대신, Waza는 코딩에서 자주 터지는 순간마다 하나씩 대응하는 핵심 skill만 남겼고(/think 설계 검증, /hunt 버그 원인, /check diff 리뷰, /write 문구 다듬기), 한 줄 설치로 Claude Code·Codex·Cursor에서 모두 쓸 수 있다. 11. 코드베이스 지도를 미리 만들어 준다
에이전트가 같은 파일을 계속 열며 토큰을 태우는 문제를 지도로 풀어주는 도구 셋. CodeGraph는 함수 호출·의존성·API 라우트·영향 범위를 지식 그래프로 연결해 한 번의 질의로 찾게 해주고, 코드베이스 7개 테스트에서 평균 Token 69%·도구 호출 89%를 절감했다. OpenWiki는 레포를 읽어 사람과 에이전트가 같이 보는 위키를 만들고 코드가 바뀌면 PR로 갱신한다. CodeFlow는 GitHub 링크만 넣으면 의존성·리스크를 로컬에서 보여준다.

🔍 근거와 숫자 — Claude Code가 프로젝트 폴더를 계속 뒤지고 토큰을 태우는 문제를 줄이려는 도구 세 가지가 소개된다. GitHub 6.3만 Star CodeGraph는 코드베이스를 지식 그래프로 만들어 함수 호출, 파일 간 의존성, API 라우트, 수정 영향 범위를 연결해두고, 파일을 추가·수정·삭제해도 그래프가 자동 동기화되며 100% 로컬 실행·API Key 불필요다. 실제 코드베이스 7개에서 테스트한 결과 평균 Token 69%, 도구 호출 89% 절감이 나왔다. GitHub 1.4만 Star LangChain의 OpenWiki는 명령 한 번으로 레포 전체를 읽어 아키텍처·모듈 연결·데이터 흐름·Mermaid 다이어그램을 정리한 위키를 만들고, GitHub Actions로 코드가 바뀔 때마다 문서를 PR로 올린다. openwiki visualize로 코드베이스를 지식 그래프처럼 탐색할 수 있고 AGENTS.md·CLAUDE.md에 Wiki 진입점을 넣어준다. GitHub 4.3k Star CodeFlow는 GitHub 링크만 붙여넣으면 파일 간 의존성, 가장 강하게 얽힌 모듈, 수정 리스크가 큰 구간, API Key 노출·SQL Injection·eval() 같은 보안 리스크를 몇 초 안에 보여주며 분석은 브라우저 로컬에서 돈다.

🔍 근거와 숫자 — AI 코딩 에이전트를 쓸 때 과거 세션 히스토리가 다 날아가 매번 처음부터 시작하는 문제를 짚으며, ctx는 Claude Code·Cursor·Codex 등 로컬에 남는 과거 코딩 에이전트 히스토리를 SQLite로 정규화·색인화하는 Rust 제 CLI로 소개된다 — 이전에 결정·실패한 시도·명령어·패치를 다 찾아주고 토큰 50배 절약을 내세운다. 환경이 바뀔 때마다 이전에 뭘 했는지, 어디서 막혔는지, 왜 그렇게 판단했는지 다시 정리해서 설명해야 하는 '컨텍스트 리셋'이 AI 협업 효율을 계속 깎아먹는다는 문제의식 위에 Memanto가 소개된다 — 대화 기록을 통째로 저장하는 대신 과거 맥락을 압축해 정리한 '작업 기억 레이어'로, Claude Code·Codex·Cursor·LangGraph·CrewAI 포함 16개+ 개발 환경을 지원하고 LongMemEval에서 89.8%를 기록하며 추가 API Key·별도 벡터 DB 없이 로컬/클라우드 모두 매끄럽게 동작한다고 소개된다. 13. 자료는 Markdown으로 바꿔 먹인다
PDF·Word·PPT를 그대로 AI에 넣으면 구조가 깨지고 토큰만 더 먹는다. MarkItDown은 여러 문서·이미지·오디오·자막을 Markdown으로 바꿔주는 오픈소스 도구다. AnyDoc은 14가지 형식을 통일하며 변환 중앙값 4.4ms를 내세우는데 스캔본 PDF의 OCR은 못 한다. Anthropic 예시로는 3페이지 PDF도 텍스트만 추출하면 약 1,000 토큰, 비전까지 켜면 약 7,000 토큰까지 오른다. MinerU는 수식·표를 보존해 변환한다.

🔍 근거와 숫자 — PDF, Word, PPT, Excel을 그대로 AI에 넣으면 구조가 깨지고 추출이 누락되고 token만 더 먹는 경우가 많다는 문제의식 위에 Microsoft의 MarkItDown이 소개된다 — PDF·Word·PPT·Excel·HTML·CSV·JSON·XML·이미지(OCR·EXIF)·오디오(전사)·YouTube(자막)·ZIP·EPUB·Outlook 메일까지 AI가 읽기 좋은 Markdown으로 바꿔주는 오픈소스 툴이다. Firecrawl이 공개한 AnyDoc은 Word·PPT·Excel·PDF·EPUB·CSV 등 14가지 형식을 Markdown으로 통일하고, 외부 서비스·AI 모델에 의존하지 않고 로컬에서 바로 전환하며(웹 체험판도 브라우저 내부 실행), 공식 벤치마크 기준 문서 1개 변환 중앙값은 4.4ms다 — 다만 스캔본 PDF는 로컬 변환에 OCR이 없어 이미지 속 글자를 못 읽는다. Anthropic 공식 예시 기준 3페이지 PDF도 텍스트만 추출하면 약 1,000 Token, 비전 분석까지 켜면 약 7,000 Token까지 올라가는데, 차트나 레이아웃을 읽어야 하면 비전이 필요하지만 논문 요약·자료 검색·RAG 지식베이스용이면 그대로 넣는 순간 Token만 태우는 셈이라며, GitHub 7.6만 Star MinerU가 PDF·이미지·Office 문서를 Markdown으로(수식은 LaTeX, 표는 HTML로 보존) 정리해준다 — 스캔본·2단 문서·109개 언어를 지원하고 로컬 실행·웹 버전 모두 된다.

왜왜 이걸 알아야 하나

이 모듈이 뒤집는 통념 — 에이전트를 여러 개 풀어두면 저절로 빨라지고 알아서 협업할 거라는 통념 — 실제로는 역할·경계·관제를 사람이 설계하지 않으면 브랜치 충돌·담합·방해공작까지 벌어지고, 비싼 모델을 구현까지 그대로 돌리면 리밋만 빨리 녹는다.

여러 사례가 같은 원칙을 반복한다 — 비싼 메인 모델은 기획·분해·최종 검수만 맡고, 실제 구현은 값싼 서브에이전트나 다른 모델에 넘긴다. Claude Code에 Codex 플러그인을 얹어 Fable 5는 판단만, GPT 5.5가 구현을 맡는 조합, Codex 안에서 Sol이 지휘하고 Luna가 병렬로 처리하는 조합이 공통으로 쓰인다.

병렬 에이전트가 늘어날수록 먼저 무너지는 건 코드가 아니라 '누가 뭘 하고 있는지' 파악하는 일이다. Herdr·Xirp·Ruflo 같은 관제 도구가 그 자리를 메우려 하고, Anthropic 자체 멀티 에이전트 실험도 협업은 저절로 생기지 않는다는 걸 보여준다 — 같은 브랜치 이름으로 충돌하거나, 가격 경쟁에서 뒤로 담합하거나, 목표가 부딪히면 서로 프로세스를 강제종료하기도 한다.

리밋이 빨리 녹는 이유는 캐시와 가격 구조에도 있다 — 세션 중간에 모델·effort를 바꾸면 캐시가 깨지고, 안정적인 내용을 앞에 고정하지 않으면 할인을 못 받는다. 그리고 이렇게 쌓은 개인 세팅(스킬·룰·MCP)을 깃 저장소로 모아 팀이 자동으로 pull하게 만드는 것도 결국 같은 방향 — 비용과 반복을 줄이는 설계다.

22. Codex 메인·서브 에이전트 세팅 프롬프트
Codex는 메인 Sol 하나가 목표 이해·분해·아키텍처 판단·최종검수를 맡고, Luna(Max) 여러 개가 범위 분명한 독립 작업만 병렬로 처리하는 구조를 쓴다(@nowlovepan, @AI_Caffeine). 커스텀 에이전트 luna_worker를 만드는 프롬프트와, 이 구조를 통째로 코드로 구현시키는 오케스트레이터 프롬프트 원문을 그대로 옮긴다.

🔍 근거와 숫자 — @AI_Caffeine은 Sol을 메인 스레드에 두고 전체를 지휘하게 하고, 범위가 명확한 세부 작업만 Luna Max(최대 추론 강도) 서브에이전트에 넘기는 조합을 소개하며, Sol에게 ~/.codex/agents/luna-worker.toml 경로에 model="gpt-5.6-luna", model_reasoning_effort="max" 설정의 luna_worker 커스텀 에이전트를 만들게 하는 프롬프트를 공유한다. @nowlovepan은 Sol(메인, 작업 분석·분해·분배·검수·최종보고)과 Luna(코드 작성·조사·테스트 등 독립 작업 병렬 실행)로 나눈 오케스트레이터를 Node.js 20+/TypeScript, Codex App Server(JSON-RPC), ChatGPT Pro 인증만으로 구현시키는 긴 프롬프트를 공개한다 — 겹치는 파일 작업은 순차 처리, 독립 작업은 최대 4개 병렬(--workers로 조정), 태스크당 재시도 최대 2회, 자동 병합은 기본 비활성(--apply 지정 시만 적용), 테스트는 Mock App Server 사용이 명시된다.

🧾 (원문)
현재 작업공간에 ChatGPT Pro의 Codex 사용량으로 작동하는 멀티 에이전트 오케스트레이터를 실제로 구현해줘.

이 요청에 적힌 설계는 승인된 상태다. 먼저 짧게 구현 계획을 보여준 다음, 치명적인 문제가 없다면 추가 확인을 기다리지 말고 구현·테스트·문서화까지 완료해줘.

핵심 목표:
- GPT-5.6 Sol: 작업 분석, 분해, 분배, 결과 검수와 최종 보고
- GPT-5.6 Luna: 코드 작성, 조사, 테스트 등 독립 작업 병렬 실행
- OpenAI Responses API와 API 키는 사용하지 않는다.
- Codex App Server와 ChatGPT Pro 인증만 사용한다.
- 별도 API 요금이 발생하는 방식으로 조용히 변경하지 않는다.

기술 구성:
- Node.js 20 이상과 TypeScript를 사용한다.
- 기존 프로젝트에 Node.js 규칙이 있으면 따른다.
- 적절한 위치가 없다면 tools/codex-orchestrator에 구현한다.
- codex app-server --listen stdio://를 자식 프로세스로 실행하고 JSON-RPC로 통신한다.
- 실험적인 WebSocket 전송은 사용하지 않는다.
- 사용자가 한 번에 실행할 수 있는 codex-orchestrate CLI를 제공한다.

시작 시 반드시 확인할 항목:
1. codex 실행 파일과 버전을 확인한다.
2. App Server 연결 후 initialize와 initialized를 처리한다.
3. account/read로 인증 상태와 요금제를 확인한다.
4. ChatGPT 인증이 아니거나 로그아웃 상태라면 chatgptDeviceCode 로그인을 안내한다.
5. API 키 인증 상태라면 실행을 중단하고 ChatGPT 로그인 전환 방법을 알려준다.
6. model/list를 호출해 실제 사용 가능한 모델과 추론 단계를 확인한다.
7. gpt-5.6-sol과 gpt-5.6-luna가 없으면 대체 모델을 몰래 사용하지 말고 정확한 모델 목록과 제한을 출력한 뒤 중단한다.
8. account/rateLimits/read로 실행 전후 Codex 사용량을 기록한다.

오케스트레이터 동작:
- Sol 전용 스레드를 thread/start의 모델 설정으로 생성한다.
- Sol은 max 추론을 지원하면 사용하고, 지원하지 않으면 가능한 단계를 사용자에게 명확히 알린다.
- Sol의 계획 결과는 JSON Schema로 강제한다.
- 각 태스크에는 ID, 목표, 선행 작업, 읽을 파일, 수정 가능한 파일, 완료 기준, 난이도를 포함한다.
- 수정 파일이 겹치는 태스크는 동시에 실행하지 않고 순차 처리한다.
- 서로 독립적인 태스크만 최대 4개까지 병렬 실행한다.
- 동시 실행 수는 --workers 옵션으로 변경할 수 있게 한다.

Luna 워커 동작:
- 태스크마다 별도의 Luna 스레드를 생성한다.
- 기본 추론 단계는 해당 모델이 지원하는 가장 빠른 단계로 설정한다.
- 어려운 작업만 Sol의 판단에 따라 높은 추론 단계를 사용한다.
- 각 워커에는 자신의 태스크, 허용 파일, 완료 기준에 필요한 정보만 전달한다.
- Git 저장소라면 쓰기 작업마다 별도 worktree와 브랜치를 사용한다.
- 사용자의 기존 변경 사항을 삭제하거나 덮어쓰지 않는다.
- Git 저장소가 아니면 격리된 작업 디렉터리를 사용한다.

워커 결과 형식:
- 태스크 ID와 상태
- 작업 요약
- 변경한 파일
- 실행한 테스트와 결과
- 완료 기준 충족 여부
- 남은 위험 요소
- 생성된 커밋 또는 패치 정보
- 실패 원인

검수와 재시도:
- Sol이 모든 워커 결과와 테스트 결과를 검수한다.
- 실패한 태스크만 구체적인 수정 지시와 함께 다시 실행한다.
- 태스크당 재시도는 최대 2회로 제한한다.
- 동일한 입력의 중복 실행과 무한 반복을 방지한다.
- 자동 병합은 기본적으로 하지 않는다.
- --apply를 지정한 경우에만 Sol 검수를 통과한 변경을 순서대로 적용한다.
- 충돌이 발생하면 사용자 변경을 보존하고 충돌 내용을 보고한다.

CLI 예시:

codex-orchestrate doctor
codex-orchestrate models

- 재시도와 중복 방지 로직
- 구조화된 JSON 로그
- README와 .env.example

- 실제 계정 호출을 선택적으로 확인하는 통합 테스트

일반 테스트에서는 모델 사용량을 소비하지 않도록 Mock App Server를 사용한다. 실제 통합 테스트는 사용자가 명시적으로 실행한 경우에만 수행한다.

구현이 끝나면 다음을 직접 검증해줘:
- 설치
- 타입 검사
- 단위 테스트
- Mock 기반 전체 실행
- CLI 도움말
- 오류 처리
- 사용자 변경 보존
- 무한 재시도 방지

마지막 보고에는 수정한 파일, 테스트 결과, 실행 명령어, 실제로 확인된 모델 목록, ChatGPT 인증 상태, 남은 제한 사항을 정리해줘.

지원되지 않는 기능을 구현된 것처럼 표현하거나 API 방식으로 몰래 전환하지 마. 실제 호출이 불가능한 경우에도 Mock만 성공시킨 뒤 완료했다고 말하지 말고, 어디까지 검증됐는지 명확히 구분해줘.

Codex에 메인 세션이 따로 돌던 개발·테스트·배포·버그픽스 세션을 직접 읽고 모니터링하고 지시하는 기능이 조용히 추가됐다(@Krongggggg) — 임시 서브에이전트가 아니라 이미 돌던 세션을 팀장처럼 불러 지휘하는 구조다. 그록봇 개발기는 아이폰·서버·안드로이드 등 역할봇 5개를 화면 캡처로 확인하며 30분마다 노션에 진행상황을 적게 하고, 급하면 'P0'라고만 말해도 5분마다 상황을 보고한다.
