모듈 1

⚖️ 권한 출처를 섞지 않는다

에이전트의 실패는 대개 머리가 나빠서가 아니라, 무엇을 근거로 삼을지가 섞여서 난다.

dryforge 는 이 문제를 "모델 성능"이 아니라 판단 권한의 배치 문제로 본다. 익숙한 패턴을 근거로 말하지 않은 제품 규칙을 만들어 내고, 현재 코드를 의도된 동작의 증거로 오해하고, 구현하기 쉬운 방향으로 명세를 다시 해석하고, 자기 설명을 완료 증거로 받아들인다 — 하나하나는 그럴듯한데 결과는 사용자 의도에서 멀어진다.

🗂️여섯 출처가 정하는 것, 그리고 정하지 않는 것

권한을 가진 주체를 여섯으로 쪼개고, 각자에게 정할 수 있는 것과 절대 정하면 안 되는 것을 같이 준다. 오른쪽 칸이 이 표의 핵심이다 — 보통 하네스는 "누가 뭘 정한다"만 적고 "무엇은 정하지 않는다"를 안 적는다.

🧊code 는 "현재 사실"이지 "원하는 동작"이 아니다

에이전트는 눈앞의 코드를 근거로 삼기 쉽다. 코드는 지금 무엇이 돌아가고 있는지만 증명한다. 그게 옳은지는 증명하지 않는다. 이 둘을 섞으면, 잘못 구현된 것이 곧 명세가 된다.

Existing code is legacy: a HOW reference and a reality-check, never the authority for WHAT.src/skills/ready/SKILL.md:30-33

migration 쪽에서 같은 규칙이 한 번 더 강해진다. 코드는 인증 검사가 무엇을 하는지는 보여주지만, 그것이 정책 전부인지는 증명하지 못한다.

Code can show what the auth check does but not whether it is the whole policy; it shows a state field but not which transitions are forbidden by the business.src/skills/migration/references/migration-elicit.md:32-34
바로 쓰는 판정 — "코드가 이러니까 이게 맞다"가 나오면 멈춘다. 코드로 답할 수 있는 건 현재 무엇을 하는가뿐이다. 무엇을 해야 하는가는 사용자나 승인된 명세에서만 나온다.
⛏️입력은 캐야 할 광석이지 다듬을 초안이 아니다

잘 쓰인 요구사항 문서를 받으면 그대로 믿고 싶어진다. dryforge 는 문서가 존재한다는 사실이 그게 좋은 문서라는 증거는 아니다라고 못박는다. 입력의 내용은 귀하게 쓰되 권위는 내린다.

A long requirements doc spat out by a coding tool is a brain-dump that never had a design conversation; the existence of a document is not evidence it is a good one. Authority comes from dialogue + user approval, not from where the input came from.src/skills/ready/SKILL.md:24-26

그래서 입력을 제자리에서 다듬지 말라고 한다. 다듬는 순간 초안이 정본으로 굳는다.

The moment you polish the INPUT as a draft, it hardens into ground truth — that is authority creep... The INPUT is ore to mine, not a draft to polish.src/skills/ready/references/decompose.md:8-11
내 하네스에 대면 — planning-generator 는 입력을 구조화한다(PRD/FS/IA/UF). 구조화는 다듬기에 가깝다. 갈라지는 지점이 정확히 여기다: 구조화 전에 출처별로 분해하고 충돌을 표시하는 단계가 내 쪽엔 없었다.
🤝작업 명세와 프로젝트 제약이 부딪히면 — 사용자가 둘 다 바꾼다

이번 작업의 spec 과 프로젝트에 오래 쌓인 규칙이 충돌할 때, 한쪽이 조용히 다른 쪽을 덮어쓰면 드리프트가 시작된다. 답은 "누가 이기나"가 아니라 둘 다 멈추고 사용자에게 간다이다.

The spec does not override the harness — the user's decision changes both at once. Domain conflicts don't self-resolve; the user always decides.src/skills/go/references/harness-format.md:351-357

이건 규모의 문제다. spec 은 한 사이클짜리 기준이고 harness 는 프로젝트 수명짜리 제약이다. 수명이 다른 두 문서를 같은 평면에서 비교하면 짧은 쪽이 항상 이긴다.

바로 쓰는 판정 — 지금 작업이 기존 규칙을 어겨야 한다면, 그건 구현 판단이 아니라 규칙 변경 요청이다. 규칙 변경은 사용자 결재 사항이다.
실습 (15분) — 내 프로젝트에서 최근 커밋 3개를 고르고, 각 변경의 근거가 여섯 출처 중 어디였는지 적어본다. code 에서 나온 것이 하나라도 있으면 그 결정은 다시 봐야 한다. 그리고 "이건 사용자가 정해야 했는데 내가 정했다"에 해당하는 것이 몇 개인지 센다.
모듈 2

📐 floor, not ceiling

절차를 자세히 쓸수록 모델은 일이 아니라 절차에 최적화된다.

↔️순정 에이전트와 과잉 하네스는 양쪽에서 실패한다

아무 제약 없는 에이전트는 사용자의 의미가 아직 비어 있을 때 자유가 너무 많다 — 익숙한 기본값이 아무도 말한 적 없는 요구사항으로 굳는다. 반대로 절차를 빽빽하게 적은 하네스는 모델을 절차 만족 기계로 만든다.

순정 에이전트는 사용자의 의미가 아직 불완전한 시점에 너무 많은 자유를 가집니다. 그래서 익숙하고 합리적인 기본값을 보이지 않는 요구사항으로 만들 수 있습니다. 반대로 절차를 지나치게 자세히 정한 하네스는 모델을 실제 작업보다 절차 자체에 최적화시킵니다.README_ko.md:139

dryforge 의 답이 floor, not ceiling 이다. 바닥만 못박는다 — 의도에는 근거가 있어야 하고, 동작에는 정본이 있어야 하고, dependency 는 명시돼야 하고, 완료에는 증거가 있어야 하고, 중요한 지식은 실행 뒤에도 남아야 한다. 그 위는 모델의 판단에 맡긴다.

🔩엄격함은 딱 한 곳에만 — 기계가 읽는 그래프

전부 엄격하게 만들면 전부 형식이 된다. dryforge 는 3문서 중 단 한 블록만 기계 판독 스키마로 두고, 나머지는 사람이 읽고 고치기 쉬운 산문으로 남긴다.

exactly ONE part is a rigid, machine-parsed schema — the Execution Graph. The three documents' bodies are content requirements: the agent designs the structure per project.src/skills/ready/references/output-format.md:5-8

그 한 블록조차 인코딩되는 판단은 하나다 — 어느 작업이 어느 작업을 필요로 하는가(depends). 파도(wave)는 인코딩하지 않고 소비자가 위상정렬로 유도한다. 인코딩하면 두 곳에서 관리해야 하니까.

tasks: - id: T5 depends: [T2, T3] # 유일하게 인코딩된 판단 risk: RISKY # 선택 — 테스트 의식의 크기만 정한다 regen_barriers: - { after: [T3], run: "<프로젝트에서 발견한 재생성 명령>" }
Do not encode produces / consumes / shared_write / waves... waves are derived by go (topological sort of depends).src/skills/ready/references/dependency-calc.md:21-27
내 하네스에 대면 — 내 룰에는 표가 많고 표마다 같은 요구사항이 반복된다. 같은 규칙이 skill-quickref·auto-triggers·thinking-flow 세 곳에 조금씩 다르게 적혀 있었다. dryforge 원칙은 올바른 기준 문서에 한 번만 적으라는 것이다.
🪶입력이 짧다고 명세가 얇아져서는 안 된다

절차의 크기는 작업에 맞춘다. 작은 수정에 큰 조율 비용을 물릴 이유는 없다. 그러나 입력이 한 줄이라고 명세까지 한 줄이 되면 안 된다 — 오히려 반대다.

그러나 입력이 짧다는 이유로 명세까지 얇아져서는 안 됩니다. 입력에서 도출할 수 있는 내용이 적을수록 구현 전에 더 많은 의도를 확정해야 합니다. 비용은 결과에 영향을 주지 않는 작업을 줄여서 낮추며, 결과를 증명하는 기준을 낮추지는 않습니다.README_ko.md:145

같은 규칙이 elicitation 쪽에 한 문장으로 다시 나온다 — A thin input raises the bar (ask more), never lowers it. src/skills/ready/SKILL.md:247

실습 (20분) — 내 상시 로드 룰을 열고 문장마다 물어본다. "이 문장을 읽은 에이전트와 안 읽은 에이전트가 다른 결과를 내는가?" 아니면 그 문장은 장식이다. 그다음 "이 문장이 없으면 무엇이 깨지나"에 답 못 하는 문장을 센다.
모듈 3

🎣 보상 해킹 저항

하네스는 의도하지 않아도 보상 구조를 만든다. 가장 재기 쉬운 것이 목표를 대신한다.

📉뒤에 게이트가 있으면 앞단은 게이트 통과 최소치로 수렴한다

체크리스트를 자세히 주면 칸 채우기가 목표가 된다. 뒤에 강한 검사가 있으면 앞단은 그 검사를 간신히 통과하는 산출물로 수렴한다. 지시를 더 붙여도 안 고쳐지고, 대리 목표만 정교해진다.

자세한 checklist는 칸 채우기 목표가 될 수 있습니다. 뒤에 강한 gate가 있으면 앞단은 그 gate를 간신히 통과하는 산출물로 수렴할 수 있습니다... 지시를 더 많이 추가한다고 해결되지 않으며, 오히려 대리 목표만 정교해질 수 있습니다.README_ko.md:248

그래서 해법이 "지시 추가"가 아니라 배치 변경이다.

목표는 모델이 shortcut을 택할 수 없을 때까지 구속하는 것이 아닙니다. 가장 짧은 유효 경로가 사용자가 의도한 결과와 일치하도록 판단 권한, 증거, 정보의 배치를 설계하는 것입니다.README_ko.md:258
🚨게이트가 잡은 건 게이트의 성공이 아니다 — 앞단의 실패다

이 한 문장이 dryforge 에서 가장 날카롭다. 보통은 "게이트가 잡았으니 시스템이 잘 돌아간다"고 읽는다. dryforge 는 반대로 센다. 게이트에 도달한 결함은, 앞단이 대화를 너무 일찍 닫았다는 증거다.

A load-bearing gap that reaches the gate is an ELICIT failure, not a gate success: it means you closed the dialogue while real design was still unsettled... 🪞 A=A — 만든 놈이 판정 못 한다

저자는 자기 누락을 구조적으로 볼 수 없다. 게으름이 아니라 구조다.

🔍저자가 잘하는 것과 구조적으로 못 하는 것

명세의 결함은 두 종류다. 충실도(대화에서 정한 게 문서에 제대로 들어갔나)와 완전성(대화가 아예 다루지 않은 게 있나). 저자는 첫째를 가장 잘 보고, 둘째는 원리적으로 못 본다.

의도를 저술했나강한 곳약한 곳
저자 리뷰예 — 세션을 쥐고 있다충실도완전성 (자기 누락을 못 본다 = A=A)
독립 검증아니오완전성충실도 (세션을 본 적 없다)
a completeness gap is something the dialogue never named at all... Holding only the session, REVIEW(A) has nothing to compare it against — you cannot diff against what was never said — so it is structurally blind to this class, not merely careless.src/skills/ready/references/review-fidelity.md:36-41
핵심 — A=A 가 불신하는 것은 보는 것이 아니라 저술한 것이다. 독립 검증자는 대화를 읽어도 된다. 다만 그 결정을 내리지 않았어야 한다.
🧩관점을 나누고, 입력도 같이 나눈다

같은 리뷰를 여러 번 반복하는 구조가 아니다. 네 관점이 서로 다른 결함을 찾고, 각자 다른 입력을 받는다. 입력이 같으면 관점만 늘어나고 사각지대는 그대로다.

관점언제받는 입력찾는 것

🧮서브에이전트는 딱 두 곳 — 그것도 "독립"이 필요할 때만

🧾 완료는 자신감이 아니라 증거다

평가하지 못한 검사는 실패다. 조용하다고 통과가 아니다.

🚦evidence floor — 명령을 돌렸다는 사실은 증거가 아니다

모든 실행 경로에 증거 바닥이 있다. 무엇이 증거인지는 프로젝트마다 다르지만, 공통 규칙은 하나다 — 명령을 실행했다는 사실이 아니라 주장한 동작을 실제로 입증해야 한다.

평가할 수 없었던 검사는 실패로 취급합니다. 검증 명령이 assertion에 도달하기 전에 종료되거나, 서비스를 관찰할 수 없거나, 외부 작업의 결과를 확인할 방법이 없다면 눈에 띄는 오류가 없다는 이유로 성공을 추론하지 않습니다.README_ko.md:236

같은 리뷰가 더 아픈 걸 잡았다. 테스트 22개가 전부 통과하는데, 규칙을 고의로 깨는 변형 네 개를 넣어도 여전히 전부 통과했다. 그중 하나는 handoff 의 하드 게이트였다.

문서가 말하는 것 대신, 같은 방법을 돌려서 실제로 나온 것.

🔐먼저 — 이 플러그인은 내가 호출할 수 없다

설치된 플러그인의 세 스킬은 frontmatter 에 disable-model-invocation: true 가 박혀 있다. 그래서 내 스킬 목록에 아예 안 뜬다. README 의 "사용자가 명시적으로 호출할 때만 실행됩니다"가 말이 아니라 구조로 강제돼 있다.

실측 · ~/.claude/plugins/cache/dryforge/dryforge/1.1.1/skills/*/SKILL.md
name: ready disable-model-invocation: true allowed-tools: Read, Edit, Write, Bash, Grep, Glob, Agent, AskUserQuestion

그래서 이 부록의 사이클은 내가 스킬 원문을 읽고 그 방법을 손으로 따라 실행한 것이다. 슬래시로 /dryforge:ready 를 부른 것이 아니다. 진짜 플러그인 경로를 보려면 사용자가 직접 쳐야 한다.

이 자체가 bounded autonomy 다 — 경계를 문장으로 부탁하지 않고 메타데이터로 못박았다. 내가 "도움이 되려고" 대신 호출하는 경로가 아예 없다.

여기서 본 것 — 그 답을 내가 혼자 정했다면 "보수적으로 합치는 게 친절하다"를 골랐을 것이다. 그리고 그건 도구가 확인하지 못한 사실을 단정하는 것이었다. 도메인 결정을 사용자에게 돌린 것의 값이 이만큼이다.
