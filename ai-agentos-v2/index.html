A-1. 아마존 50개 팀 실측: 도구가 아니라 방식이 갈랐다
같은 AI 코딩 도구를 받은 50개 팀 중 절반은 3배 미만에서 멈췄고, 나머지 절반은 중앙값 4.5배(일부 10배 이상)를 기록했는데 그 차이는 "일하는 방식을 의도적으로 바꿨는가"였다.

📊 데이터 — AWS 시니어 프린시펄 엔지니어 클레어 리고올(키로 개발자)이 2026년 6월 AI 엔지니어 월즈 페어에서 공개 00:00~00:27. - 아마존 스토어(아마존닷컴+각국 리테일+오프라인 매장) 산하, 신입~시니어가 섞인 "평범한" 50개 팀을 2025년 대부분 기간 관찰, 지표는 커밋 수가 아닌 프로덕션 배포 속도 05:33~06:51. - 결과: 절반은 3배 미만, 나머지 절반은 중앙값 4.5배·일부 10배 이상 06:51~07:18. 90%가 키로 등 사내 도구를 썼지만 "도구가 아니라 일하는 방식"이 차이였다 07:18. - 대조 사례 ①: 베드록 추론 데이터 플레인 재구축 — 원래 견적 30명·18개월 → 6명이 76일 만에 완성(최대 20배 개선). 단, 팀원이 분산 시스템·LLM 전문가(디스팅귀시드 엔지니어 2명 포함)라 일반화하기 어려움 02:51~04:38. - 대조 사례 ②: 프라임 비디오 6인 파일럿 — 프로젝트 납기 추정 90주→24주(73% 단축), 커밋 96개→556개(5.8배). 단, 온콜·회의 없이 방해 없는 10일이었고 시니어가 사전 3주간 요구사항을 다 쪼개 놓은 상태였음 04:38~05:05.

🔍 습관 5가지 — (4.5배 팀 인터뷰에서 추출, 07:48~14:00): 1. 에이전트 컨텍스트에 투자: 슬랙 대화·온보딩·코드리뷰로 암묵적으로 전수하던 지식을 스킬/스티어링 파일에 명문화. 두 습관성 질문 — "에이전트가 틀릴 때마다 파일에 뭐가 빠졌나?", "새 모델이 나오면 이 규칙이 아직 필요한가?"(오래된 모델 버릇 방지용 규칙이 컨텍스트 부채가 되는 것을 방지) 07:48~08:40. 2. "느려져야 빨라진다": 새 방식 도입 직후 거의 모든 팀에서 생산성이 먼저 떨어짐. 이유는 코드베이스 쪽 선행 작업(컨텍스트 축적, 도구 에러 메시지 개선, 신규 MCP 서버 제작, 코드베이스 구조 재편, 심지어 Python/JS→TypeScript/Rust로 언어 전환)이 먼저 필요하기 때문 08:40~10:28. 3. 베이비시팅 대신 먹이 주기: 30초~1분마다 결과를 확인하고 다시 지시하는 "왕복형" 대화는 에이전트 병렬 실행을 막아 4~5배가 나올 수 없는 구조를 만든다. 할 일과 함께 스스로 확인할 방법(테스트 통과, 커버리지 90%, 통합 테스트 검증까지)을 같이 주면 에이전트가 스스로 품질 기준을 넘을 때까지 돌고 필요할 때만 돌아온다 10:28~12:41. 4. 의도를 코드보다 먼저 명문화(스펙 주도 개발): 애매하고 복잡한 기능은 코드 전에 목표·사용자·핵심 기능·기술 요구사항을 스펙 문서로 작성(초안은 모델에게 시켜도 됨). 코드 전체에 흩어진 변경을 놓고 왕복하는 것보다 문서 한 장을 놓고 왕복하는 게 훨씬 저렴하다는 논리 12:41~13:34. 5. 테스트를 왼쪽으로 당기기: 린터·유닛·통합·성능·보안 테스트를 촘촘히 붙여 빠른 피드백 루프를 만들어야 에이전트가 몇 시간을 자율로 돌 수 있음. 특히 외부 서비스를 목(mock)으로 바꿔 통합 테스트를 로컬에서 완결시키는 방식이 많이 쓰임 13:34~14:00.
